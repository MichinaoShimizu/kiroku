# Security policy

kiroku reads AI agent histories that can contain private prompts, file paths and commit messages. Security reports are taken seriously.

## Reporting a vulnerability

Please report vulnerabilities privately through [GitHub's private vulnerability reporting](https://github.com/MichinaoShimizu/kiroku/security/advisories/new) (Security → Report a vulnerability). Do not open a public issue, and do not attach real agent history.

Reports in English or Japanese are welcome. You can expect a first response within a week.

## Scope

Especially relevant areas:

- AI agents: kiroku runs no AI agent and calls no AI service; its `--ai` options were removed in 4.0 and do nothing (see [Options](docs/guide.md#options)). `kiroku serve` has no `/ai/run` (it answers 404).
  - Review and report prompts: the session review and each day's report offer "Copy prompt": it copies the prompt to the clipboard when you press it, and kiroku runs nothing and sends nothing. Where you paste it is your choice. The prompt names your history files, and text in them (web pages, tool output, other people's repositories) can try to steer an agent that reads them (prompt injection), so use an agent you'd trust with your history.
  - Earlier runs: sessions an agent kept of runs from kiroku 1.x–3.x (recorded in a temporary `kiroku-ai-` folder) are still left out, so they never show up as your sessions.
- `kiroku serve`: it shows the view, its data and history files only to a browser that has its key, so that other users of the same computer can't read your history through it.
  - The key: The key is 32 random bytes kept in `serve-key` in kiroku's settings folder (`0600`, folder `0700`, also when the folder already existed; a key file others can read is replaced).
  - Opening a browser: A browser gets it through a one-time code. `kiroku serve` (unless `--no-open`, also when it finds one already running at that address and opens that) creates 32 random bytes, stores only the SHA-256 of the port and the code as an empty `0600` file in `open-codes` (a real folder, `0700`) in the same settings folder, and opens the view with `?code=<code>`.
  - The one-time code: A `GET` of that address returns a small `no-store` page without the key and doesn't use the code, so a link preview or prefetch gets nothing. The page's one script (allowed by its CSP hash, which allows only same-origin requests) trades the code for the key with a `POST` that needs `X-Kiroku: 1` and a same-origin `Origin`, as `/archive` does. A code works once, within 10 minutes, and only on the port it was made for; `kiroku serve` deletes its file before answering, ignores code files others can read or that are symbolic links, and expired files are removed the next time a code is made.
  - Storing the key: The script checks that the key is 64 hex digits, keeps it in the browser's `localStorage` for that origin (scheme, host and port) and replaces the address. Browsers keep visited addresses in their history (and sync them when history sync is on), so only a spent code ends up there, never the key. An address with `?key=<key>` (made by versions before v0.38.2) is refused with the page that says how to open kiroku, even when the key is right: such an address stays in the browser's history with the key in it.
  - In the browser: The view sends the key in an `X-Kiroku-Key` header with every request that returns history or changes something (`/data.json`, `/stamp`, `/progress`, `/prompt`, `/reply`, `/history`, `/archive`), and kiroku compares it in constant time.
  - No cookie: The key is never kept in a cookie, and a cookie is not accepted as the key (an older version's `kiroku_key_<port>` cookie is expired whenever a browser sends it). Browsers don't separate cookies by port, and `SameSite` doesn't stop a cookie going to another port of the same host, so a cookie would be sent to any other server on `localhost` (perhaps run by another user of the computer) when you type its address, follow a link to it or the browser fetches its icon.
  - `localStorage` is not sent anywhere by the browser and is readable only by pages of the same origin; the view's Content-Security-Policy allows only its own scripts, which send the key only back to the same origin. This doesn't protect against another user who listens on the same port while `kiroku serve` is stopped: a page served there is the same origin and can read the stored key.
  - Command lines and other devices: kiroku never puts the key on a browser's command line (visible to other users): it opens a `0600` HTML file that forwards to the view. kiroku 5.0 removed `--print`, which printed an address with a one-time code for another device; kiroku no longer prints the key or a code.
  - Without the key: Only `GET /` and `GET /manifest.webmanifest` answer without the key. `/` returns the page without any history in it (or the loading page); the manifest, which lets Chrome and Edge install the view as an app, is a fixed document built from constants (name, start URL `/` and the icons as `data:` PNGs), and the view's Content-Security-Policy allows it with `manifest-src 'self'` only in `kiroku serve`. There is no service worker, so the browser keeps no copy of the view or history for the app; the page reads the history from `/data.json` with the header and shows how to open it with `kiroku serve` when it has no key. The history file of a session is fetched the same way and saved from a `blob:` URL.
  - Where it listens: It listens on `127.0.0.1` only (a bare port such as `:8485` also stays on `127.0.0.1`) and rejects requests whose Host is not `localhost`, `127.0.0.1`, `[::1]`, the address it listens on or a name added with `--allow-host` (DNS rebinding protection). Listening on another address such as `0.0.0.0:8484` must be chosen explicitly; it then also answers this computer's own IPs and host name, and still rejects any other Host.
  - History files: It serves an original history file (`.json`, `.jsonl`, or `.jsonl.zst` decompressed, only) only for sessions in the current snapshot, and only when the file (after following symbolic links) is inside a location kiroku reads history from or the `kiroku serve --archive` folder; session IDs read from history that contain path separators, `..` or drive names are rejected.
  - HTTP: It has no write timeout (history files can be large) but limits how long a client may take to send its headers and how large they may be. Every response carries `X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and same-origin `Cross-Origin-Opener-Policy` / `Cross-Origin-Resource-Policy`. Error responses don't include local paths; the details go to the terminal
- Files kiroku writes: `kiroku serve --archive` keeps its copies in folders only you can open (`0700`, files `0600`). The folders it copies into are made `0700` even when they already existed, since their names show session IDs and project folders; the archive folder itself is set to `0700` when kiroku creates it, so pick one that isn't shared. `kiroku serve --archive off` deletes only the `.zst` copies kiroku saved, and only in a folder marked by `kiroku serve --archive on`. kiroku copies history only after `kiroku serve --archive on` (or "Back up to this folder" under "Data sources" in `kiroku serve`, whose `POST /archive` needs the key, `X-Kiroku: 1` and a same-origin `Origin`, and can only turn it on, in the folder given when `kiroku serve` started), and only history an agent deletes by itself; copying by default would need a decision recorded here first
- Reading history: only regular files are opened (a named pipe, device or folder in a history location is reported as unreadable instead of being opened, so it can't block `kiroku serve` or `kiroku serve --archive`; on Unix the file is opened non-blocking and checked again after opening), lines longer than 64 MiB are skipped (and reported as unreadable) instead of being read into memory, JSON files larger than 64 MiB are not read, and zstd-compressed history is decoded with a 1 GiB memory limit and only up to 1 GiB decompressed per file (a small `.zst` that expands further is reported as unreadable, and `kiroku serve` cuts off its `/history` download, instead of decoding it for minutes)
- Symbolic links in history folders: when reading (and when `kiroku serve --archive` keeps copies), kiroku follows symbolic links, so a history folder or file that is a link to somewhere else is read like the original (this keeps setups that move history to another disk working). Anyone who can write into your history folders can therefore make kiroku show and keep a copy of another file you can read, if it is in an agent's history format. `kiroku serve` never serves such a file through `/history` unless the resolved file is inside a location kiroku reads history from or the `kiroku serve --archive` folder
- Private conversations: Kiro Crew conversations held in incognito or temporary mode are shown with counts and times only, under a fixed title. Their prompts, replies, title and files are kept out of the view and the prompts kiroku builds for an AI, and so are their copies in other agents' histories that kiroku can match (see the Kiro Crew note in [docs/guide.md](docs/guide.md)). `kiroku serve --archive` may still keep their files, as it keeps any history an agent deletes
- git: kiroku runs `git` only to read commits and pushes in folders named by your history, which may be repositories someone else made. It ignores the system git config (`GIT_CONFIG_NOSYSTEM=1`) and overrides the repository's settings that run programs (`core.fsmonitor`, `core.hooksPath`, `core.pager`, `log.showSignature`, and `--no-ext-diff --no-textconv` for `git log`), never fetches anything (`protocol.allow=never`, `GIT_ALLOW_PROTOCOL=none`, which the repository's `protocol.<name>.allow` can't override, and `GIT_NO_LAZY_FETCH=1`, so a partial clone doesn't download missing files or run the repository's `remote.<name>.uploadpack`), never prompts (`GIT_TERMINAL_PROMPT=0`) and takes no optional locks. Your global git config is still read, since `user.email` (to show only your commits) and `safe.directory` live there. On Windows, network (UNC) paths from history are skipped
- `kiroku serve --check --report` and "Format check": kiroku never sends diagnostics. `--report` prints kiroku's version, OS and architecture, and per agent the number of sessions, the newest agent version seen in history, the number of lines that couldn't be parsed, and record kinds kiroku doesn't know with their counts, for you to review and paste yourself. It contains no paths, project names, branch names, session or message IDs, prompt or reply text, or home folder. Kind names from history are kept only if they match `[A-Za-z0-9_.:-]{1,40}` (anything else is counted as `other`), at most 20 per agent; versions only as digits and dots. The same fields appear in "Data sources" (escaped).
- Terminal output (such as `kiroku serve --check` and errors about files that could not be read) prints text from history with control characters and Unicode format characters removed, so history can't send escape sequences (colors, window titles, clipboard writes) to your terminal
- Login items: kiroku 5.0 registers none. `kiroku autostart` only removes the one kiroku 4 registered, at its fixed path (the launchd agent `io.github.michinaoshimizu.kiroku` on macOS, the systemd user service `kiroku.service` on Linux), and writes nothing
- The generated HTML: user data must be escaped, and nothing should be sent off the machine. The page carries a Content-Security-Policy that allows only its own inline script and stylesheet (by hash), no external resources, and network requests only back to `kiroku serve` (none for the static demo page), and `translate="no"`, so browsers don't offer to send its text to a translation service.
  - Commands it copies for pasting into a terminal (resuming a session, `git -C <repo> show` for a commit or push) quote every value from history or git, and are left out when a value can't be quoted safely. The git command carries `--no-pager`, `-c core.fsmonitor=false`, `--no-ext-diff` and `--no-textconv`, so pasting it doesn't run the pager, fsmonitor, external diff, textconv or `filter.*.process` commands that a repository someone else made can set in its `.git/config`.
  - The resume command quotes the folder and session ID read from history for the shell: single quotes on macOS and Linux, where a value with `'` or `\` gets no command, because fish and PowerShell read those inside single quotes differently from sh; double quotes on Windows, where a value with `%`, `!`, `$` or a backtick gets no command. A value with control characters, Unicode format characters (such as bidirectional overrides or zero-width spaces), curly quotes (U+2018–U+201F, which PowerShell reads as quotes), or a leading `-` (which a command would read as an option even when quoted) gets no command
- Prompts for an AI agent: the prompts the view builds escape Markdown, put history inside a fenced block, keep each value on one line (so line breaks in history can't forge lines that look like kiroku's), and mark history as data, not instructions. The review and report prompts name history files for an AI agent on the same computer to read and ask it to read only those; the agent then reads everything in them, which is why the view and the guide say to use an agent you trust
- `install.sh` and `kiroku update`: releases are verified against `checksums.txt` from the same release before replacing the binary. `kiroku update` accepts only version names of the form `v1.2.3` (or `v1.2.3-rc.1`), follows only `https` redirects, extracts only a regular file of at most 200 MiB, and installs an older version only with `--force`. A `kiroku update` that downloads from the public repository does not check attestations itself; one that updates through `gh` does (next item). kiroku checks for a newer release only when you run `kiroku update` (or `kiroku serve --check`, unless `--no-update-check`); it never asks on its own while other commands run. When the GitHub CLI (`gh`) is installed, `install.sh` also checks the artifact attestation with `gh attestation verify` (signer workflow `release.yml`, source ref `main` or the release tag, GitHub-hosted runners only) and stops if it does not match. It only warns when `gh` is not logged in or cannot reach GitHub, and checks for a mismatch first, since `gh`'s message quotes values from the certificate (a branch or workflow name) that whoever made the release can choose; `KIROKU_REQUIRE_ATTESTATION=1` makes any failure to check fatal (including a missing `gh`), and `KIROKU_SKIP_ATTESTATION=1` skips the check. The script body runs from its last line only, so a truncated `curl | sh` download does nothing
- `kiroku update` in a build from another repository: a release built by `release.yml` in any repository other than `MichinaoShimizu/kiroku` (for example an organization's private copy) embeds that repository (`HOST/OWNER/REPO`, from `GITHUB_SERVER_URL` and `GITHUB_REPOSITORY`) at build time; nothing at run time (no environment variable, file or flag) can change it. Its `kiroku update` and the update check of `kiroku serve --check` then run the GitHub CLI (`gh release view` and `gh release download`), found in `PATH` (only as an absolute path, never in the current folder), directly with fixed arguments and no shell, so that `gh`'s login reaches a private repository. kiroku never reads, stores or passes a token. The embedded name must be of the form `HOST/OWNER/REPO` with no part starting with `-`, and the version `gh` reports must be a version name as above, or nothing is run or downloaded. `gh` writes the file to kiroku's memory (at most 200 MiB), which is checked against `checksums.txt`. Before anything is replaced, kiroku also runs `gh attestation verify` on the archive (written to a temporary folder only you can read) with the same rules as `install.sh`: signer workflow `HOST/OWNER/REPO/.github/workflows/release.yml`, source ref `main` or the release tag, GitHub-hosted runners only. It stops if the provenance is missing or does not match, also stops (saying so) when `gh` is not logged in (exit code 4), only warns when this `gh` is too old or cannot reach the host, and honours `KIROKU_REQUIRE_ATTESTATION=1` and `KIROKU_SKIP_ATTESTATION=1` the same way; `gh`'s error message is shown with control and format characters removed. `gh` is stopped at a time limit (30 seconds to check the version, 5 in `serve --check`, 30 minutes for a download, 2 minutes for each provenance check), and kiroku waits at most a few seconds more for anything `gh` started that still holds its output. Without `gh`, or without access, it stops and never falls back to the public repository. Builds of `MichinaoShimizu/kiroku` don't embed anything and never run `gh`
- Official price pages: kiroku itself never fetches prices. Only the weekly `Prices` workflow in CI (`.github/workflows/prices.yml`) fetches Anthropic's and OpenAI's pricing pages with `tools/prices`, which parses only the expected tables strictly (numbers and model IDs of a fixed form) and executes nothing from them. The job that fetches has a read-only token; the job that opens an issue with the difference has only `issues: write` and runs no repository code. Price changes reach `internal/core` only through a reviewed pull request
- Releases are built by GitHub Actions and carry artifact attestations (see "Verifying a release" below). Workflows pin third-party actions to commit SHAs, give each job only the permissions it needs, and the release build does not use the Actions cache

Only the latest release is supported.

## Automated checks

- [CodeQL](https://github.com/MichinaoShimizu/kiroku/actions/workflows/codeql.yml) analyzes the Go code and the view's JavaScript on every pull request, every push to main and weekly; findings go to the repository's code scanning alerts
- [OpenSSF Scorecard](https://scorecard.dev/viewer/?uri=github.com/MichinaoShimizu/kiroku) checks the repository's security practices (pinned dependencies, token permissions, branch protection and so on) weekly and on every push to main, and publishes the result
- Go fuzz tests feed broken and crafted input to the history readers, the git remote parser and the HTML view (which must keep all history out of its one script). CI runs their seeds on every pull request, and the [Fuzz](https://github.com/MichinaoShimizu/kiroku/actions/workflows/fuzz.yml) workflow fuzzes each one weekly and on every push to main
- CI runs `govulncheck` (known vulnerabilities in code kiroku calls) and `staticcheck`, and checks that no script runs in a view built from history full of HTML and script payloads
- Dependabot proposes updates to Go modules, GitHub Actions and the npm packages used in tests every week, and security fixes right away

## Verifying a release

Each release archive comes with an SPDX SBOM (`<archive>.sbom.json`) that lists the Go version and every Go module, with its version, built into the binary. The standalone binaries (`kiroku-<os>-<arch>`, `.exe` on Windows) have no SBOM of their own; each holds the same binary as its archive. The archives, the standalone binaries, the SBOMs and `checksums.txt` all carry build provenance. Releases have SBOMs from v0.14.0 and Sigstore bundles (below) from v0.15.0. In the commands below, replace `X.Y.Z` with the version you downloaded.

Check that a file was built by this repository's release workflow (needs the [GitHub CLI](https://cli.github.com/)):

```bash
gh attestation verify kiroku_X.Y.Z_linux_amd64.tar.gz --repo MichinaoShimizu/kiroku
```

Each release also includes the same provenance as a signed Sigstore bundle, `kiroku_<version>.sigstore.json`. With it, `gh` checks the files without looking the attestation up on GitHub (it still fetches Sigstore's public keys):

```bash
gh attestation verify kiroku_X.Y.Z_linux_amd64.tar.gz --repo MichinaoShimizu/kiroku --bundle kiroku_X.Y.Z.sigstore.json
```

Check that a release binary is exactly what its tag's source produces. The build is reproducible: `tools/reproduce.sh` clones the tag, builds it the way `.goreleaser.yaml` does (with the Go toolchain named in the tag's `go.mod`, `CGO_ENABLED=0`, `-trimpath`, `-ldflags "-s -w -X main.version=<version>"`), downloads the release archive, checks it against `checksums.txt` and compares the two binaries byte for byte. It needs git, Go, curl and tar (and unzip for Windows targets), and can check any target from any OS.

```bash
sh tools/reproduce.sh vX.Y.Z linux amd64     # os: darwin, linux, windows; arch: amd64, arm64
```

By hand, that is:

```bash
git clone --branch vX.Y.Z https://github.com/MichinaoShimizu/kiroku.git && cd kiroku
GOTOOLCHAIN=goA.B.C GOENV=off GOFLAGS= GOEXPERIMENT= CGO_ENABLED=0 GOOS=linux GOARCH=amd64 GOAMD64=v1 \
  go build -trimpath -ldflags "-s -w -X main.version=X.Y.Z" -o kiroku .
sha256sum kiroku     # compare with the kiroku in kiroku_X.Y.Z_linux_amd64.tar.gz
```

Take `goA.B.C` from the `toolchain` line of the tag's `go.mod` (without one, `go` plus the version on its `go` line, such as `go1.26.0`), as `tools/reproduce.sh` does. `GOENV=off` and the empty `GOFLAGS` and `GOEXPERIMENT` keep your own Go settings out of the build; for arm64, use `GOARM64=v8.0` instead of `GOAMD64=v1`.

Build from a clean clone of the tag, not from a source tarball or a modified tree: Go records the module version and commit in the binary, so a different commit or uncommitted changes give a different binary. Only the binaries are compared, not the archives around them.
