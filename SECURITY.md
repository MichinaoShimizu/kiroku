# Security policy

kiroku reads AI agent histories that can contain private prompts, file paths and commit messages. Security reports are taken seriously.

## Reporting a vulnerability

Please report vulnerabilities privately through [GitHub's private vulnerability reporting](https://github.com/MichinaoShimizu/kiroku/security/advisories/new) (Security → Report a vulnerability). Do not open a public issue, and do not attach real agent history.

Reports in English or Japanese are welcome. You can expect a first response within a week.

## Scope

Especially relevant areas:

- `kiroku serve --ai` (off by default): only then does the view's `POST /ai/run` run an agent (`claude -p` with only the Read tool and only the history folders added with `--add-dir`, `codex exec --sandbox read-only`, or `kiro-cli chat --no-interactive`) in an empty temporary folder, so the instructions and settings of the folder kiroku serve was started in don't apply, with a prompt the browser sends, after the person confirms each run. The endpoint keeps the key, Host, `X-Kiroku` and same-origin checks, accepts only a numeric loopback listen address, one run at a time, a 256 KiB prompt, a 2-minute limit and 1 MiB of output, and never runs a command string from the request, nor an agent whose command isn't found. The agent runs in a process group of its own (on Unix), which is killed when the run stops, and kiroku stops reading its output shortly after, so a process the agent started can't keep a run going past its limit. The run is streamed back as one JSON object per line (the fixed command line, the agent's reply, the tools Claude Code uses and the agent's stderr, with terminal escape sequences and control characters removed, at most 1 MiB), and the view shows all of it as text: the formatted reply is built from elements with their text set as text, never as HTML, loads no images and makes no links clickable. The agent may send the prompt and the history it reads to its provider; without `--ai` the endpoint answers 403 and the view shows "Analyze with AI (off)", which only explains how to turn it on
- `kiroku serve`: it shows the view, its data and history files only to a browser that has its key, so that other users of the same computer can't read your history through it. The key is 32 random bytes kept in `serve-key` in kiroku's settings folder (`0600`, folder `0700`, also when the folder already existed; a key file others can read is replaced). A browser gets it by opening the view with `?key=<key>`: that answer is a small page, holding no key itself, whose one script (allowed by its CSP hash) checks that the key in the address is 64 hex digits, keeps it in the browser's `localStorage` for that origin (scheme, host and port) and replaces the address with one without the key, so the key stays out of the address bar and the browser's history. The view then sends it in an `X-Kiroku-Key` header with every request that returns history or changes something (`/data.json`, `/stamp`, `/progress`, `/prompt`, `/reply`, `/history`, `/archive`, `/ai/run`), and kiroku compares it in constant time. Only `GET /` answers without the key, and it returns the page without any history in it (or the loading page); the page reads the history from `/data.json` with the header and shows how to open it with `kiroku open` when it has no key. The history file of a session is fetched the same way and saved from a `blob:` URL. The key is never kept in a cookie, and a cookie is not accepted as the key: browsers don't separate cookies by port, and `SameSite` doesn't stop a cookie going to another port of the same host, so a cookie would be sent to any other server on `localhost` (perhaps run by another user of the computer) when you type its address, follow a link to it or the browser fetches its icon. A `kiroku_key_<port>` cookie left by an older version is expired whenever a browser sends it. `localStorage` is not sent anywhere by the browser and is readable only by pages of the same origin; the view's Content-Security-Policy allows only its own scripts, which send the key only back to the same origin. Like the cookie before it, this doesn't protect against another user who listens on the same port while `kiroku serve` is stopped: a page served there is the same origin and can read the stored key. kiroku never puts the key on a browser's command line (visible to other users): it opens a `0600` HTML file that forwards to the view. `kiroku open --print` prints the address with the key for another device; on a network it travels unencrypted. It listens on `127.0.0.1` only (a bare port such as `:8485` also stays on `127.0.0.1`) and rejects requests whose Host is not `localhost`, `127.0.0.1`, `[::1]`, the address it listens on or a name added with `--allow-host` (DNS rebinding protection). Listening on another address such as `0.0.0.0:8484` must be chosen explicitly; it then also answers this computer's own IPs and host name, and still rejects any other Host. It serves an original history file (`.json`, `.jsonl`, or `.jsonl.zst` decompressed, only) only for sessions in the current snapshot, and only when the file (after following symbolic links) is inside a location kiroku reads history from or the `kiroku archive` folder; session IDs read from history that contain path separators, `..` or drive names are rejected. It has no write timeout (history files can be large) but limits how long a client may take to send its headers and how large they may be. Every response carries `X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and same-origin `Cross-Origin-Opener-Policy` / `Cross-Origin-Resource-Policy`. Error responses don't include local paths (except `/ai/run`, which returns the end of the agent's own error output to the view); the details go to the terminal
- Files kiroku writes: `kiroku html` and `kiroku json` write through a temporary file in the same folder that is renamed into place, readable only by you (`0600`), so a symbolic link at the destination is replaced rather than followed. `kiroku archive` keeps its copies in folders only you can open (`0700`, files `0600`). The folders it copies into are made `0700` even when they already existed, since their names show session IDs and project folders; the archive folder itself is set to `0700` when kiroku creates it, so pick one that isn't shared. `kiroku archive off` deletes only the `.zst` copies kiroku saved, and only in a folder marked by `kiroku archive on`
- Reading history: only regular files are opened (a named pipe, device or folder in a history location is reported as unreadable instead of being opened, so it can't block `kiroku stats`, `kiroku serve` or `kiroku archive`; on Unix the file is opened non-blocking and checked again after opening), lines longer than 64 MiB are skipped (and reported as unreadable) instead of being read into memory, JSON files larger than 64 MiB are not read, and zstd-compressed history is decoded with a 1 GiB memory limit and only up to 1 GiB decompressed per file (a small `.zst` that expands further is reported as unreadable, and `kiroku serve` cuts off its `/history` download, instead of decoding it for minutes)
- git: kiroku runs `git` only to read commits and pushes in folders named by your history, which may be repositories someone else made. It ignores the system git config (`GIT_CONFIG_NOSYSTEM=1`) and overrides the repository's settings that run programs (`core.fsmonitor`, `core.hooksPath`, `core.pager`, `log.showSignature`, and `--no-ext-diff --no-textconv` for `git log`), never fetches anything (`protocol.allow=never`, `GIT_ALLOW_PROTOCOL=none`, which the repository's `protocol.<name>.allow` can't override, and `GIT_NO_LAZY_FETCH=1`, so a partial clone doesn't download missing files or run the repository's `remote.<name>.uploadpack`), never prompts (`GIT_TERMINAL_PROMPT=0`) and takes no optional locks. Your global git config is still read, since `user.email` (to show only your commits) and `safe.directory` live there. On Windows, network (UNC) paths from history are skipped
- `kiroku doctor --report` and "Format check" ([ADR 0032](docs/adr/0032-user-mediated-diagnostics.md)): kiroku never sends diagnostics. `--report` prints kiroku's version, OS and architecture, and per agent the number of sessions, the newest agent version seen in history, the number of lines that couldn't be parsed, and record kinds kiroku doesn't know with their counts, for you to review and paste yourself. It contains no paths, project names, branch names, session or message IDs, prompt or reply text, or home folder. Kind names from history are kept only if they match `[A-Za-z0-9_.:-]{1,40}` (anything else is counted as `other`), at most 20 per agent; versions only as digits and dots. The same fields appear in "Data sources" (escaped) and in `kiroku json` (`meta.report[]`). In the view, "Copy diagnostics" copies the same text, built from those fields and sanitized again; "Report a problem" opens GitHub's new-issue page with only fixed values in its address (kiroku version, OS and architecture, view language, current screen), since an address is sent to GitHub when opened, and never history or diagnostics
- `kiroku stats` prints names from history (agents, models, projects) to the terminal with control characters and Unicode format characters removed, so history can't send escape sequences (colors, window titles, clipboard writes) to your terminal
- `kiroku autostart` refuses values with control characters (such as newlines) when writing the systemd unit
- The generated HTML: user data must be escaped, and nothing should be sent off the machine. The page carries a Content-Security-Policy that allows only its own inline script and stylesheet (by hash), no external resources, and network requests only back to `kiroku serve` (none for a saved HTML file), and `translate="no"`, so browsers don't offer to send its text to a translation service. The prompts it builds for an AI agent escape Markdown. The AI prompts put history inside a fenced block, keep each value on one line (so line breaks in history can't forge lines that look like kiroku's), and mark history as data, not instructions. The review and report prompts name history files for an AI agent on the same computer to read and ask it to read only those; the agent then reads everything in them, which is why the view and the guide say to use an agent you trust. Commands it copies for pasting into a terminal (resuming a session, `git -C <repo> show` for a commit or push) quote every value from history or git, and are left out when a value can't be quoted safely. The resume command it shows for pasting into a terminal quotes the folder and session ID read from history for the shell (single quotes on macOS and Linux; double quotes on Windows, where a value with `%`, `!`, `$` or a backtick gets no command), and a value with control characters, Unicode format characters (such as bidirectional overrides or zero-width spaces), curly quotes (U+2018–U+201F, which PowerShell reads as quotes), or a leading `-` (which a command would read as an option even when quoted) gets no command
- `install.sh` and `kiroku update`: releases are verified against `checksums.txt` from the same release before replacing the binary. `kiroku update` accepts only version names of the form `v1.2.3` (or `v1.2.3-rc.1`), follows only `https` redirects, extracts only a regular file of at most 200 MiB, and installs an older version only with `--force`. `kiroku update` does not check attestations itself. When the GitHub CLI (`gh`) is installed, `install.sh` also checks the artifact attestation with `gh attestation verify` (signer workflow `release.yml`, source ref `main` or the release tag, GitHub-hosted runners only) and stops if it does not match. It only warns when `gh` is not logged in or cannot reach GitHub; `KIROKU_REQUIRE_ATTESTATION=1` makes any failure to check fatal (including a missing `gh`), and `KIROKU_SKIP_ATTESTATION=1` skips the check. The script body runs from its last line only, so a truncated `curl | sh` download does nothing
- Official price pages: kiroku itself never fetches prices. Only the weekly `Prices` workflow in CI (`.github/workflows/prices.yml`) fetches Anthropic's and OpenAI's pricing pages with `tools/prices`, which parses only the expected tables strictly (numbers and model IDs of a fixed form) and executes nothing from them. The job that fetches has a read-only token; the job that opens an issue with the difference has only `issues: write` and runs no repository code. Price changes reach `internal/core` only through a reviewed pull request
- Releases are built by GitHub Actions and carry artifact attestations (see "Verifying a release" below). Workflows pin third-party actions to commit SHAs, give each job only the permissions it needs, and the release build does not use the Actions cache

Only the latest release is supported.

## Automated checks

- [CodeQL](https://github.com/MichinaoShimizu/kiroku/actions/workflows/codeql.yml) analyzes the Go code and the view's JavaScript on every pull request, every push to main and weekly; findings go to the repository's code scanning alerts
- [OpenSSF Scorecard](https://scorecard.dev/viewer/?uri=github.com/MichinaoShimizu/kiroku) checks the repository's security practices (pinned dependencies, token permissions, branch protection and so on) weekly and on every push to main, and publishes the result
- Go fuzz tests feed broken and crafted input to the history readers, the git remote parser and the HTML view (which must keep all history out of its one script). CI runs their seeds on every pull request, and the [Fuzz](https://github.com/MichinaoShimizu/kiroku/actions/workflows/fuzz.yml) workflow fuzzes each one weekly and on every push to main
- CI runs `govulncheck` (known vulnerabilities in code kiroku calls) and `staticcheck`, and checks that no script runs in a view built from history full of HTML and script payloads
- Dependabot proposes updates to Go modules, GitHub Actions and the npm packages used in tests every week, and security fixes right away

## Verifying a release

Each release archive comes with an SPDX SBOM (`<archive>.sbom.json`) that lists the Go version and every Go module, with its version, built into the binary. The archives, the SBOMs and `checksums.txt` all carry build provenance. (SBOMs start with the first release after v0.13.3.)

Check that a file was built by this repository's release workflow (needs the [GitHub CLI](https://cli.github.com/)):

```bash
gh attestation verify kiroku_0.13.3_linux_amd64.tar.gz --repo MichinaoShimizu/kiroku
```

From the first release after v0.14.0, each release also includes the same provenance as a signed Sigstore bundle, `kiroku_<version>.sigstore.json`. With it, `gh` checks the files without looking the attestation up on GitHub (it still fetches Sigstore's public keys):

```bash
gh attestation verify kiroku_0.15.0_linux_amd64.tar.gz --repo MichinaoShimizu/kiroku --bundle kiroku_0.15.0.sigstore.json
```

Check that a release binary is exactly what its tag's source produces. The build is reproducible: `tools/reproduce.sh` clones the tag, builds it the way `.goreleaser.yaml` does (with the Go toolchain named in the tag's `go.mod`, `CGO_ENABLED=0`, `-trimpath`, `-ldflags "-s -w -X main.version=<version>"`), downloads the release archive, checks it against `checksums.txt` and compares the two binaries byte for byte. It needs git, Go, curl and tar (and unzip for Windows targets), and can check any target from any OS.

```bash
sh tools/reproduce.sh v0.13.3 linux amd64     # os: darwin, linux, windows; arch: amd64, arm64
```

By hand, that is:

```bash
git clone --branch v0.13.3 https://github.com/MichinaoShimizu/kiroku.git && cd kiroku
GOTOOLCHAIN=go1.26.9 CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
  go build -trimpath -ldflags "-s -w -X main.version=0.13.3" -o kiroku .
sha256sum kiroku     # compare with the kiroku in kiroku_0.13.3_linux_amd64.tar.gz
```

Build from a clean clone of the tag, not from a source tarball or a modified tree: Go records the module version and commit in the binary, so a different commit or uncommitted changes give a different binary. Only the binaries are compared, not the archives around them.
