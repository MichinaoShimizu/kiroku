# kiroku guide

This guide supplements the [README](../README.md). It covers installation and commands in detail, how to read the view, metric definitions, which histories are read, and options.

## Install

### macOS and Linux (recommended)

```bash
curl -fsSL https://raw.githubusercontent.com/MichinaoShimizu/kiroku/main/install.sh | sh
```

This downloads the file for your OS and CPU (Intel / Apple Silicon and ARM) from [Releases](https://github.com/MichinaoShimizu/kiroku/releases), verifies it with `checksums.txt`, and places it in `/usr/local/bin` (or `~/.local/bin` if that is not writable). You can set the version and install location with environment variables.

```bash
curl -fsSL https://raw.githubusercontent.com/MichinaoShimizu/kiroku/main/install.sh | KIROKU_VERSION=v0.1.7 KIROKU_INSTALL_DIR=~/bin sh
```

| Variable | Meaning |
| --- | --- |
| `KIROKU_VERSION` | The version to install (e.g. `v0.1.7`). The latest if not set |
| `KIROKU_INSTALL_DIR` | Where to place `kiroku`. `/usr/local/bin` if not set (`~/.local/bin` if that is not writable) |
| `KIROKU_SKIP_ATTESTATION=1` | Do not check the build provenance with `gh`, even if it is installed (also for `kiroku update` in a build from your organization's repository) |
| `KIROKU_REQUIRE_ATTESTATION=1` | Require the build provenance check: stop instead of installing when `gh` is missing or not logged in, cannot reach GitHub, or the version is older than v0.12.0 |

`install.sh` checks each download against `checksums.txt` and, when the [GitHub CLI](https://cli.github.com/) (`gh`) is installed, its build provenance (see [Verifying a release](../SECURITY.md#verifying-a-release)). You can also check a file you downloaded yourself:

```bash
gh attestation verify kiroku_<version>_darwin_arm64.tar.gz --repo MichinaoShimizu/kiroku
```

### Windows

Download `kiroku_<version>_windows_<amd64 or arm64>.zip` from [Releases](https://github.com/MichinaoShimizu/kiroku/releases) and extract it.

### Go

Go 1.26 or later is required.

```bash
go install github.com/MichinaoShimizu/kiroku@latest
```

> On macOS, opening a `kiroku` downloaded with a browser may show "“kiroku” Not Opened" (because it is not notarized by Apple). `install.sh` and `go install` do not trigger this warning. If you downloaded it with a browser, run `xattr -d com.apple.quarantine ./kiroku`, or open it with "Open Anyway" in System Settings → Privacy & Security.

### With the GitHub CLI

Each release also has the binary on its own: `kiroku-darwin-arm64`, `kiroku-darwin-amd64`, `kiroku-linux-amd64`, `kiroku-linux-arm64`, `kiroku-windows-amd64.exe` and `kiroku-windows-arm64.exe`. With the [GitHub CLI](https://cli.github.com/), one command downloads it to a place you choose (files `gh` downloads get no quarantine attribute on macOS):

```bash
gh release download -R MichinaoShimizu/kiroku -p kiroku-darwin-arm64 -O ~/bin/kiroku.new \
  && gh attestation verify ~/bin/kiroku.new --repo MichinaoShimizu/kiroku \
     --signer-workflow MichinaoShimizu/kiroku/.github/workflows/release.yml --deny-self-hosted-runners \
  && chmod +x ~/bin/kiroku.new && mv ~/bin/kiroku.new ~/bin/kiroku
```

This checks the file's build provenance (made by `release.yml` on a GitHub-hosted runner) before it replaces anything in `~/bin`. If the check fails, nothing is replaced; delete `~/bin/kiroku.new` before you try again (`gh release download` doesn't overwrite a file). The binaries are also listed in `checksums.txt`, like the archives.

### Inside an organization (a private repository)

To hand kiroku out from your organization's own GitHub repository, private or internal, push this repository there under any name and push a `v*` tag: `release.yml` builds and publishes the release in that repository. A build made in any repository other than `MichinaoShimizu/kiroku` remembers where it was built (`HOST/OWNER/REPO`), and its `kiroku update` and the update check of `kiroku serve --check` ask that repository through the GitHub CLI and its login, so they reach a private repository. kiroku keeps no token of its own, and verifies the download with `checksums.txt` as usual.

For the people who use it:

```bash
gh auth login                                                   # once
gh release download -R your-org/your-repo -p kiroku-darwin-arm64 -O ~/bin/kiroku.new \
  && gh attestation verify ~/bin/kiroku.new --repo your-org/your-repo \
     --signer-workflow your-org/your-repo/.github/workflows/release.yml --deny-self-hosted-runners \
  && chmod +x ~/bin/kiroku.new && mv ~/bin/kiroku.new ~/bin/kiroku
kiroku serve
kiroku update                                                   # later: updates from your-org/your-repo
```

On Windows, download `kiroku-windows-amd64.exe` (or `-arm64.exe`) the same way to a new file such as `-O "$env:LOCALAPPDATA\Programs\kiroku\kiroku.new.exe"`, check it with the same `gh attestation verify` line, then rename it to `kiroku.exe` and add that folder to your `PATH`.

- `kiroku update` there needs `gh` installed and logged in with access to the repository (with SAML single sign-on, authorize the login for the organization). Without them it stops and says what to do
- Before it replaces anything, `kiroku update` there also checks the build provenance with `gh attestation verify` (made by that repository's `release.yml` on a GitHub-hosted runner), as `install.sh` does: it stops if the provenance doesn't match, warns if `gh` is too old or can't reach the host, and follows `KIROKU_REQUIRE_ATTESTATION=1` and `KIROKU_SKIP_ATTESTATION=1`. On GitHub Enterprise Server without artifact attestations, set `KIROKU_SKIP_ATTESTATION=1`; it never falls back to the public repository
- In that repository you only need `release.yml` (and `ci.yml` if you like). The other workflows (`pages.yml`, `prices.yml`, `upstream.yml`, `scorecard.yml`, `codeql.yml`, `tag.yml`, `fuzz.yml`) are for this public repository and can be deleted. Your enterprise's Actions policy must allow the actions `release.yml` uses, and build provenance for a private repository needs GitHub Enterprise Cloud
- The links at the bottom of the view (GitHub, and the release of the running version) point to that repository too
- To put the demo page (dummy data, no one's history) on an internal web server, build it with `KIROKU_REPO=github.com/your-org/your-repo sh tools/screenshots/run.sh --html index.html` (needs Go, Python 3 and git). Its dummy data covers the five weeks up to the day it was built. Never put a view of real history on a shared server
- Take each new release of `MichinaoShimizu/kiroku` in soon: only the latest release is supported, and security fixes go there
- `tools/reproduce.sh` checks releases of `MichinaoShimizu/kiroku`. A build from your repository embeds its name, so it differs from the public binary of the same version

## Commands

| Command | Description |
|---|---|
| `kiroku serve [ADDR]` | Serves the view at `http://localhost:8484/` and keeps it up to date (see the notes below the table). Change the port with, for example, `kiroku serve :8485` (a bare port still listens on `127.0.0.1` only). Only browsers that have its key can open the view (see "[The key of kiroku serve](#the-key-of-kiroku-serve)"); the browser it opens gets the key. If `kiroku serve` is already running at that address, running it again opens the running view in your browser with its key (with `--no-open`, it only prints the address). Press Ctrl+C to quit |
| `kiroku serve --check` | Checks your setup in one go and only reads (see the notes below the table). Run it right after installing, or when something you expect is missing from the view. `kiroku serve --check --report` prints only a short block for a bug report (kiroku --version, OS, and per agent the number of sessions, newest version seen, unreadable lines and unknown kinds with counts; no paths, project names, IDs or content) for you to review and paste into a GitHub issue yourself; kiroku sends nothing |
| `kiroku serve --archive [on\|off]` | Keeps compressed copies of history that agents delete automatically (Claude Code, Kiro Crew) in kiroku's own folder (see "[Keep a copy of history in kiroku](#keep-a-copy-of-history-in-kiroku)"). With no argument, shows the status (on or off, location, number and size of files) |
| `kiroku --version` | Prints the version (also on the first line of `kiroku help`) |
| `kiroku update` | Downloads the latest release for the same OS and CPU from GitHub Releases, verifies it with `checksums.txt`, and replaces itself. In a terminal it shows how much of the download has arrived. In a location you cannot write to (such as `/usr/local/bin`), run `sudo kiroku update`. kiroku installed with `go install` or built from source (version `dev`) is not replaced unless you pass `--force`, so update it with `go install …@latest`. `--to v1.2.3` installs a chosen version (only names such as `v1.2.3` or `v1.2.3-rc.1` are accepted); going back to an older version than the one running also needs `--force`. v0.1.1 and earlier have no `update`, so reinstall once with `install.sh` or from Releases. A kiroku built in your organization's own repository updates from there with the GitHub CLI (see [Inside an organization](#inside-an-organization-a-private-repository)) |

`kiroku help` lists commands; `kiroku serve --help`, `kiroku serve --check --help`, `kiroku serve --archive --help` and `kiroku update --help` show their options.

kiroku has three commands: `serve`, `update` and `help`. `serve` also checks your setup (`--check`) and keeps copies of history (`--archive`), each chosen with its first flag. kiroku 5.0 removed the older commands: `doctor`, `archive` and `version` stop with a message naming `kiroku serve --check`, `kiroku serve --archive` and `kiroku --version`. `open` and `html` are gone with no replacement: run `kiroku serve` (again, if it is already running) to open the view; kiroku no longer writes the view to a file. `autostart` only removes a login item that kiroku 4 registered (see [Uninstall](#uninstall)).

`kiroku serve`:

- It answers right away. While it reads your history for the first time (which can take a while with a lot of history or many git repositories), the page shows "Reading your history…" with each agent as it is read (its number of sessions and how long it took), and switches to the view when it is done. The terminal shows how many sessions each agent had, how long each one took, and the total
- If the port is already in use, it stops at once without reading history
- Every few seconds it checks the history folders for changes (file names, sizes and modification times only) and reloads once writing settles: when changes stop for 10 seconds, and within 60 seconds at most even if an agent keeps writing
- New history appears while the week or month you are viewing and the selected session stay as they are, and `LIVE` is shown at the top left

`kiroku serve --check`:

- It checks which histories were found (sessions and the oldest date for each agent, and where it looked), whether an agent will delete old history (Claude Code on its 30-day default) and which settings file to change, whether `kiroku serve --archive` is on, whether git is found, whether a login item from kiroku 4's `autostart` is still there (run `kiroku autostart` to remove it), which kiroku is running, and whether a newer kiroku is out
- For a newer kiroku it asks GitHub Releases while it reads history; `--no-update-check` skips this, and builds from source are not checked
- Agents with no history yet are summed up in one line, so the lines that ask you to do something stay in view; `--all` lists each of them with the place kiroku looks
- If another kiroku comes first in your `PATH`, so that `kiroku` runs that one instead, it says so
- Under "Format check" it shows, per agent, the newest agent version seen in history, lines that couldn't be read and record kinds kiroku doesn't know, with counts (see [How histories are read](sources.md#format-check)); unknown kinds can mean the agent changed its history format
- It ends with what to run next, including `kiroku update` when a newer release exists

The old forms `kiroku --serve`, `--json`, `-o` and `--weekly` / `--monthly` have been removed; kiroku names the command to use instead.

## View

- Today is marked quietly: a "Today" badge, its date in the accent color (underlined in the month calendar) and a very light background on its column in the week calendar, with no outline around the day.
- The vertical week calendar shows sessions as bars. Each bar is filled with a tint of its Color by color (agent or project) and has a stripe of that color on its left edge; the more messages per minute, the stronger the tint (from about a fifth to two fifths of the color), and sessions that overlap in time are placed side by side. Short bars show their name in smaller type, and bars too short for that show it just below when there is room. In narrow bars, names wrap between words and are shortened with "…"; a bar too narrow for the first word (or about 4 letters) shows its start time instead, or only its color when even that does not fit. Hover or click it for the name
- Choose **Week** or **Month** in the **Period** group at the top. Click a date, or "W##" on the left of the month calendar, to go to that week in the week calendar
  - Every number in the calendar and the band above it carries a unit, in English also in the Japanese view: "5 commits" (1 commit), "44 credits" (1 credit), "12M tokens", "$2.22", "3h", "4h 50m". On a phone, the month calendar puts the unit on the line under the number rather than leave it out
  - Figures in the legend row picks what the calendar writes for each day: estimated cost (the default), Kiro credits, tokens or active time, among those with records in the period; the choice is remembered and also sets the month calendar's shade.
- Each day heading of the week calendar shows its Git commits first, with a commit mark, then its usage and active time, such as "4 commits  $4.29  5h 9m" (the commit names are in the tooltip), so a day with much cost and few commits stands out; in a narrow column the figures wrap, each number staying with its unit. The commit count is in the same neutral color as the other figures (more commits is not better by itself). The month calendar shows each day's commits ("2 commits") above its usage, with the same usage as the shade of the day; the column on its left shows each week's usage, and every day's full figures are in its tooltip
  - Usage is the estimated cost; tokens when no model used in the week or month shown is in the price table; credits when it has no tokens
  - Active time shows as the length of the bars in the week calendar, and as the shading in the month calendar, where a thin bar in each day splits its active time by what Color by picks (agent or project) and follows hidden legend items and search (days with nothing left are dimmed). The week totals in the month calendar count only that month's days (the whole week is in the tooltip). Pressing a day opens its week scrolled to that day, with the day highlighted. Closing session details after moving with ← → returns to the last session read, and "This week / This month" (`T`) resets both the week and the month. ‹ stops at the first week or month with records, and a month with no records says so. Point at a day or week for its active time, sessions, tokens, estimated cost and credits
- The calendar describes recorded activity, not progress, completion or productivity
- Above the calendar, the figures for deciding what to do next (see the metrics table): what you used (what it left behind, such as Git commits, lines changed and pull requests, is in each calendar day and the summary's Output panel and card, not here)
  - On a tinted background: usage (estimated cost and Kiro credits side by side in one box, such as "$37.32 · 80 credits"; tokens instead of the cost when no model used is in the price table), A day to match last week while the week is in progress, and Month-end (estimate) in the month view while the month is in progress (in its place: the month view shows where the month is heading instead of a day's budget). While you look at the current week, Month-end credits shows where this month's Kiro credits are heading (credits are a monthly allowance); pressing it opens the month's breakdown without leaving the week. A box that shows both cost and credits opens the cost's breakdown, which links to the credits' breakdown
  - Then Active time
  - Prompts (with sessions) and usage limit hits are in the summary and open the same breakdowns from there; limit hits are also in "Worth a look". Active days are in the Active time breakdown
  - Items with no records are not shown; when the figures don't fit next to the period's name, they move to their own row; except on phones they always stay in that one row, set smaller when the window is narrower (a value that still doesn't fit ends with … and is in full in its tooltip and breakdown). All figures share one plain style
  - The change from the previous week or month in percent (such as "−22% vs last week") is not in the band: press a figure to see it next to the value in its breakdown; while the period is in progress it is compared with the same days of the previous one. When your history starts inside the previous period, there is no comparison, since the missing days would count as zero. No color marks it good or bad
- Click a key figure, or any figure in the summary, to open its breakdown in a dialog. What the metric counts is right under the figure; the finer points and what it doesn't tell you are at the end:
  - Most figures: by day, by agent, by project and, for tokens and estimated cost, by model, then the top sessions (press one to open its details). The day, agent, project and model rows come from the same totals as the figure, so they add up to it; the session figures cover each whole session, including any part outside the period
  - The month-end estimates show how they are worked out (so far ÷ days so far × days in the month), with the days still to come drawn as hatched bars at the current pace. They also give a 3σ range (about 99.7%) for the cost, credits and tokens, from how much the finished days varied (also in the figure's tooltip and the summary; in the by-day chart, dotted lines show the range for each day still to come). The by-day chart also draws a trend line, a straight line fitted to the finished days (least squares) and extended to the end of the month, and the breakdown gives the month-end if that trend continues. Days are neither independent nor normally distributed, so the range is a rough guide, and its low end never goes below what is already used
  - Usage limit hits and compactions are split by agent and by project and list each one with its session (and, for limit hits, the reset time)
  - Git commits are split by project, by whether AI made them and by which agent ran them, with the list of commits
  - The other figures in the panels: commits, pushes and pull requests list each one; focus blocks, oversized prompts and the session figures list the blocks, prompts or sessions behind them; wait time is split by how long you took to reply; and ratios such as cost per prompt show how they are worked out
- The period is written like "Sep 28 – Oct 4" or "October 2026" ("9月28日 – 10月4日" or "2026年10月" in Japanese), and the line above it says "This week", "Last week", "This month" or "Last month" when that is what you are looking at. ‹ › (or ← →) move to the previous or next week or month. You can't move past the current week or month; "This week" / "This month" brings you back to it. A period with no records is named by its week or month, such as "Week of Sep 28"
- Each day in the calendar shows its own figures, both its cost figure (the one picked in Figures: estimated cost, Kiro credits or tokens) and its active time: the commits, then "$2.86  5h 9m", in the day headings of the week calendar, and the two on two lines in each day and week total of the month calendar. Point at a bar, band or point in any chart (or touch it) to see the values for that day or item
- "Worth a look" is the set of metrics that crossed a threshold. The small warning triangle next to a metric's name in the summary marks each of them; press it to open it in a dialog in the middle of the screen, without leaving where you are: what was observed, why it matters, its 13-week trend, why it was flagged, the related sessions (press one to open its details), the threshold, and what the metric is, what it doesn't tell you and what to try. `Esc`, the × in its top-right corner or a click outside the dialog returns to what you pressed
- "Color by" Project / Agent is the selector at the start of the legend (Project by default). The legend belongs to the calendar and is not shown in the summary. The numbers in the legend are active time, split between sessions that ran at the same time like in "Where it went"; click an item to show or hide it. Active time, tokens and credits can't be split that way, so while items are hidden the key figures at the top and those under each date stay totals for all sessions and are shown in gray, with a note above the calendar. On a wide window and on a phone the legend stays in one row; when it doesn't fit, scroll it sideways: while there is more to the right, the right edge fades and shows how many items are out of view, such as "+3 ›" (press it to scroll; with the keyboard, Tab reaches every item). In the week calendar, each week picks the height of an hour (44px, or 36px when needed) that fits its working hours, from the morning start to the latest end, in the calendar
- Click a bar to show its details. On wide screens the left column is the prompt flow with times, and the right column has, from the top, what you can do (the resume command and "Copy prompt" for a review), the key numbers (active time, prompts, wait time, cost and tokens) and the rest (what was left behind: commits, pull requests, files edited by AI, each path a link to the commit on the remote when there is one; subagents; and, at the end, the history file, models used and tools used). On narrow screens the same parts come in the order: what you can do, the key numbers, the prompt flow, the rest. The keyboard (`Tab`) goes through them in that order on any width
  - When the session is behind a metric flagged in "Worth a look" for the period shown, those metrics are listed under the title; press one to open the same dialog
  - The prompt flow reads like a chat, in time order, in the shapes of a messaging app on the view's dark background: your prompts are bubbles in kiroku's purple with dark text on the right, the AI's replies are dark gray bubbles with light text on the left next to a round robot mark, each bubble with a small tail, and the time sits small beside the bubble's bottom edge (left of yours, right of the AI's) with the copy button above it. What happened between them (commits, pull requests created, usage limit hits with the reset time the message gave, interruptions, compactions, notes and subagents starting) is a dark label with white text in the middle (red for limits and interruptions). Opening a commit from the flow and pressing back returns to where you were reading
  - Each of your prompts and each AI reply has a copy button (faint until you point at it) that copies its text as recorded, to reuse it. A long prompt or reply the view cut is copied in full
  - The copy button next to **Prompt flow** copies the whole conversation, prompts and replies in order, as Markdown, to hand the work to another agent or paste it into a PR or a note
  - **Full screen** next to it (or `F`) shows only the prompt flow across the whole window, for reading a long conversation; `Esc` or the button again returns to the details. It stays on while you move to other sessions
- ‹ › at the top right of the details (or `←` `→`) open the previous or next session in time order, among the sessions that match the search and agent filter; the calendar follows to that session's week or month, and the details open at the start of its prompt flow. `↑` `↓`, `PageUp` `PageDown`, `Home` `End` and `Space` scroll the details
  - Each prompt shows how long the AI worked (from the prompt to the AI's last activity before the next prompt) and how long until you replied ("you replied after", from there to the next prompt), under the AI's reply when there is one (under the prompt otherwise), and a break of more than 30 minutes is a divider like "13:50–15:20: 1h 30m gap" (both are estimates from the history's timestamps; time while a subagent was running is not counted as a wait)
  - Prompts that look like corrections (guessed from the wording) get a dashed border and a "Correction?" tag. Slash commands you typed (such as `/review`) and `!` shell commands count as prompts and get a "Command" or "Shell" tag in their own color
  - Things that entered the conversation without you typing them (background task notifications, `<system-reminder>`, hook and command output, automatic conversation summaries, instructions sent by another agent or a schedule, the expanded text of a slash command, the steering rules and environment context older Kiro IDE versions add to your message and so on) are not counted as prompts and appear in the flow in another color, labeled with their kind
  - The AI's reply follows each prompt, with its own time, so a session reads as the conversation it was: the last thing the AI wrote back to you in that turn, in its own words, not its thinking, its tool calls or their output. The view first loads the first 160 characters (all of it when no more than 20 more would be cut), and "Load the full reply" reads it to the end. A turn where the AI only ran tools, or whose words the agent does not record, has no reply line
  - The flow shows 30 prompts first, and "Show N more prompts" shows the rest. A long prompt opens with "Show all", or "Read more (N characters)" when the prompt was cut. The view first loads the first 400 characters of each prompt (all of it when no more than 20 more would be cut), and "Load the full prompt" reads it to the end
  - "Copy prompt" under Session review copies a prompt to paste into an AI agent (such as Claude Code or Codex), asking it to review the session with advice on how you prompted and used the agent. See [Reviews and reports with your agent](#reviews-and-reports-with-your-agent)
  - A turn where the AI worked but wrote no reply shows how long it worked on the AI side, marked "no text reply"
- In the week calendar, weekday hours outside 9:00–18:00 have a slightly darker background, so work early in the morning or late at night stands out; Saturday and Sunday share one neutral background, the same as the hours outside 9:00–18:00 (no red or blue for the weekend days). The month calendar's shade of each day is a neutral gray-blue, so it is never mistaken for an agent's color. It comes in the same steps as its legend (Less … More): a day without records is unshaded, and a day with records takes one of four steps by its share of the month's highest day, so you can match any day to the legend
- In the week calendar, days with commits show commit marks on the right edge at their times (they don't overlap session bars; a commit mark is filled when run by AI; touch one to see its short hash; the number under the date is that day's commit count). When five or more commit, push and pull request marks fall within a few minutes of each other, the first two are shown with a "+N" mark under them; press it to lay out all of that day's marks, and press "−" to fold them again. Click a mark to see the commit details (subject, message body, project, branch, hash, lines added and removed per file changed, the session that made the commit, and a `git show` command). Session details list the commits made during that session
- The same right edge also shows pushes and pull requests. Pushes are read from your local `git reflog` of remote-tracking branches ("update by push"), so only pushes made from this computer appear, and only as far back as git keeps its reflog (90 days by default). Pull requests appear only when an agent created one and its result was recorded (`gh pr create` or GitHub tools in Claude Code); kiroku never asks GitHub. Both also appear in a session's prompt flow. Click a push (on the calendar or in the prompt flow) to see where it went, when, the commits it sent (each opens its commit details; up to the latest 50), the session running at the time and a `git log` command for the same range. Click a pull request to see its link, when it was created, the session that created it and the pushes and commits in that session before it (kiroku never asks GitHub, so the title, status and reviews are not shown). A commit's details show the push that sent it
- Anything that can be a link is a link
  - Git commits and files changed: if the remote (`origin`) is GitHub, GitLab, Bitbucket or similar, they open the page for that commit or file
  - A session's "Files edited by AI": a file changed by a commit made during that session opens the page for that file as of that commit
  - A session's "Pull requests created": opens pull requests created by AI (URLs that appeared in the results of `gh pr create` or GitHub tools)
  - A session's "History file" (at the end of session details): opens the original history of that session. "Open" saves it from the view (only history files of loaded sessions, inside the folders kiroku reads history from or `kiroku serve --archive`'s folder, are served, and only to the view on your machine). SQLite histories cannot be opened, so you can only copy the path
- The page shows either the calendar or the weekly or monthly summary: switch with View "Calendar | Summary" next to Week | Month (or `V`). The page always opens on this week's calendar; kiroku doesn't remember the view or Week | Month from the last time. Only the page scrolls: nothing is fixed, the top scrolls away, and the week calendar shows the whole day with no scroll of its own. 0:00–7:00 is folded at the top, at a quarter of the height as a shaded band, so the working hours fit the first screen; in a week with sessions in those hours it starts unfolded, so that work isn't squeezed. "0–7h" at the top of the hours unfolds or folds it, and kiroku remembers the choice. The day headings stick under the page header while you scroll, so you always see which day is which; on narrow windows the calendar scrolls sideways and the headings follow it. When you open this week and its work starts further down, the page opens scrolled to that hour (scroll up for the figures; not in the demo). Data sources and the footer (when the page was made, the version and a link to GitHub) are at the bottom in both views.

## Reviews and reports with your agent

For a session or a day, kiroku builds a prompt for an AI agent (such as Claude Code or Codex). The agent reads the facts in the prompt and the history files it points to, and writes a review or report in a fixed format, ending with advice from an expert on working with AI agents.

Each copies its prompt to the clipboard: "Copy prompt" under Session review in session details for a session review, and the copy icon next to each date in the week calendar for a daily report. Paste it into the agent you choose. kiroku runs no agent and sends nothing, and the message shown after copying says so. The agent you paste it into may send the prompt and the history it reads to its provider, under its own account and terms, and text in your history that other people wrote (web pages, tool output, other repositories) could steer it, so use one you'd trust with your history.

| Scope | Button | Format |
|---|---|---|
| A session | "Copy prompt" under Session review in session details | Summary, Numbers, Professional prompt assessment, Prioritized advice (up to three, each with an improved prompt), Reusable prompt playbook (an improved opening prompt and follow-up prompts for similar work) |
| A day | The copy icon next to each date with history in the week calendar (named "Copy the daily report prompt for <date>") | Summary, Numbers (next to the previous day), By project, Expert observations, Next actions |

What the prompts give the agent:

- **Numbers kiroku counted**, as a table the agent copies unchanged. A review: active time, prompts, corrections and interruptions, the median wait from an AI reply to your next prompt, Git commits (and how many AI ran), estimated cost, tokens (with subagents) and Kiro credits when the history records them, compactions and usage limit hits. A report, next to the previous day: active time, sessions and prompts, Git commits (and how many AI ran), lines changed in Git commits, and estimated cost, tokens and Kiro credits when the history records them
- **What happened**: for a review, the session ID and its history file, which the agent reads for your prompts and the replies, plus the times of what the history file does not have (commits from git, pull requests, interruptions, compactions, usage limit hits and subagents). Only when there is no history file to point to (Kiro CLI's SQLite database) does it copy the prompt flow into the prompt. For a report, time, commits (with their repository, for read-only git) and pull requests for each project, and a digest of each session: your prompts in the period and the start of the AI's reply to each (up to 20 prompts per session; when the prompt would grow past about 190 KB, fewer and shorter, then only one line per session, and the prompt says it was shortened, so it stays small enough to paste into an agent)
- **The history files**: a review asks the agent to read the session's history file first. A report asks it to write from the digests and open a history file only when a digest isn't enough, and only within the times listed for that session. For Kiro CLI (SQLite), whose history is one SQLite database, the prompts are copied in instead
- **Signals for advice**: prompts you wrote in 3 or more sessions (for a review, prompts in that session you also wrote in 3 or more sessions in the last 30 days), as candidates for a skill, a custom command or project instructions; the tools the AI used most, subagents, compactions, the main model of each session (without a per-session cost, since a session's cost can fall partly outside a report's period), short sessions with no file edits on an Opus-, Fable- or Mythos-class model (where a lighter model may be enough), conversations whose input per response grew to 4× or more, and project switches (per day in a report; in a review, the prompts you wrote in other projects while the session ran)

The agent is asked to act as a professional advisor using established prompt-engineering and engineering practice, not a kiroku-specific score. Every point names what it is based on (a figure, a prompt with its time, a commit or a signal), and points the history doesn't support are left out. Signals are offered as candidates, not verdicts:

- **A session review** assesses goal clarity, context, constraints, splitting the work, iteration, verification and use of the agent, only where the history shows them, and says what worked. Up to three prioritized pieces of advice each quote the prompt with its time, say what happened and why the change matters, give an improved prompt, and tell a gap in the prompt apart from a mistake by the model or tool and from a task that was simply uncertain. The playbook is an improved opening prompt for similar work and prompts to check in along the way
- **A report** adds up to three expert observations (progress, risks, verification, work patterns, including what went well) and up to three next actions with their reason and expected benefit, marking guesses as guesses. It doesn't treat time, prompts, tokens or commits as a measure of productivity or value. A daily report stresses actual progress, blockers and the next day's step

Things to know:

- The agent reads everything in the history files it is pointed to: your prompts, the AI's replies, tool calls and their output, and may send them to its provider. Use an agent you'd trust with them. kiroku itself sends nothing
- Only Claude Code is limited to the history files (the Read tool only). Codex runs in its read-only sandbox, which can read any file you can, with your own MCP servers and web search settings; Kiro CLI uses your own Kiro tool and permission settings. Text planted in history could steer those two to other files or to tools you trusted
- A report asks the agent to base every bullet on a commit, pull request or session in the prompt, and to copy numbers, commits and links as they are
- The prompts tell the agent that history is data, not instructions, and not to follow text in it that looks like instructions. They also ask it to leave out secrets, personal data, file contents, command output and paths on your computer (a review quotes only your prompts and the AI's prose), and not to run other commands, write files or send anything to another service (a report may run the read-only Git command it describes). Still, check a report before sharing it
- The report is written in the language you mostly write your prompts in
- In a day still in progress, the prompt says the data runs up to now. Sessions hidden in the legend are left out of reports, and so are the commits of projects hidden in the legend (when colored by project), their project sections, and signals that quote their prompts. The Numbers table still counts everything, and the prompt tells the agent to copy it unchanged without mentioning what was left out

## Weekly and monthly summary

![Weekly summary (dummy data)](summary.png)

The summary opens with an overview of charts, computed in the browser from your history (no AI). Figures are compared with your own past periods in plain words, such as "$31.23: above your usual $19.92–$27.35". The "ƒx" button next to a figure's or a chart's name shows its formulas (press it again to hide them): the same comparisons as inequalities in a monospace box, such as `$31.23 > 75th pct = $27.35` or `25th pct $13.42 ≤ $18.26 ≤ 75th pct $27.35`, and the formulas behind computed figures. The 25th and 75th pct are the values a quarter of the way from the bottom and from the top when up to your last 12 weeks or months with records are sorted (periods before your history starts are left out, and so is the week or month in which it starts partway, both here and in the trends of Worth a look and "?"; that period's tooltip says why), so half of them fall between; spread = 75th pct − 25th pct, and a value beyond 75th pct + 1.5×spread or 25th pct − 1.5×spread is marked as such. They need 4 past periods. In a period in progress, cost, time and counts are compared at their pace: pace = so far × days in the period ÷ days elapsed. Figures computed from others show their formula, such as Claude Code estimated cost per AI commit = Claude Code cost ÷ AI commits, the share outside working hours = off-hours time ÷ session time, or the difference from the previous period on the same day.

Each chart opens with a takeaway computed from the data (for example "At this pace $22.86: 4th highest of 6 weeks; −$2.45 from the median $25.31") and, where the data supports one, a next step with numbers (for example "To stay within the previous period's $31.23: at most $12.97 in the 1 day left").

- **From input to output**, under the four panels and above Breakdown, the one card wider than half the page (the full width, or three fifths of it with Estimated cost and output over time to its right on windows 1300px wide or more), headed at the same level as Input and Output, with the switch for the amount on the same line: a Sankey diagram of the amount (estimated cost, Kiro credits, tokens or session time) from agent to project (the six largest, the rest grouped) to whether the session reached a commit or PR. Bands from an agent take the agent's color; each project is one band in its own color across the project column, and the bands leaving it keep that color. Names and amounts sit on a backing in the card's color: agents to the left, outputs to the right, projects on their band in the project column, with a short line to the node when a name had to move down to make room. On screens 600px wide or less, the chart is not drawn (it would be too small to read) and the names and amounts are listed instead, by column. One sentence above it says where the whole amount went, leaving out the parts that are zero, such as "Of $15.14 estimated cost, $8.67 (57%) went to sessions with a commit or PR, $4.42 (29%) to sessions without, and $2.04 (14%) is from agents that don't record commits". Its percentages, and those in each column of the list, are rounded so that they add up to 100. Sessions count in the period they started in (as in What changed from the last period), so its total can differ from the Input panel, which counts the time and usage inside the period; its "ƒx" says so
- **Estimated cost and output over time**, to the right of From input to output on wide windows (under it on narrower ones), headed at the same level: two running totals across the period, each as a share of its own total, so the units never mix: estimated cost (Kiro credits when no session records tokens) as a solid line, and lines in Git commits, Git commits or lines edited by AI as a dashed one (a switch; the choice is remembered). A week is drawn in 6-hour steps, a month in days, up to now in a period in progress. A session's cost, and its AI-edited lines, are spread over its active time, since the history doesn't record when each part was spent; Git counts by commit time. The stretch where cost rose the most (15 points or more of the period's total) while output rose 2 points or less is shaded and named in the sentence above the chart, and the chart's "ƒx" states this rule (it may be research, waiting or going in circles; the chart doesn't say which). Pointing at a step shows its amounts. From input to output shows where the amount went; this shows when, inside the period
- **Figures**, in four compact panels that split what you put in, what came out of it, and the rate of each: two by two on wide windows, with the input side (Input over Unit cost per input) on the left and the output side (Output over Unit cost per output) on the right, split by a two-colored line with "IN" and "OUT" at its top (blue for the input side, purple for the output side, also on each panel's heading mark; neither color means good or bad). On narrower windows they stack in one column (Input, Output, Unit cost per input, Unit cost per output), each with its IN or OUT label above it. Each panel is one trend chart with a switch next to its heading that picks what it shows. A choice with nothing to show for the period is left out of the switch; the view remembers each choice and falls back to the first available one:
  - **Input**: Cost (estimated cost), Credits (Kiro credits, with this month's month-end estimate in the week view), Tokens (with the output share) or Active time. Every agent that records the amount counts toward one total: Cost and Tokens add up Claude Code, Codex and the other agents that record tokens, and Credits adds up every Kiro agent (Kiro IDE / CLI (V3), Kiro CLI (V2), Kiro CLI (SQLite) and Kiro Crew). Credits is offered when any period in the chart has credits, so periods from an agent you no longer use stay next to the current ones. When two or more agents appear in the chart, the bars of Cost, Credits and Tokens are stacked by agent in the agent's color, with a key under the chart and each agent's amount in the bar's tooltip (with one agent they are plain bars). Tokens from different agents are counted alike, though each model's tokenizer splits text a little differently. Each bar of its chart is labeled with the period's amount in short form (such as $1.2k, 44, 12M or 18h); for a period still in progress it is the amount so far. The change from the previous period is in the bar's tooltip and the figure's "vs last week" line. Next to the figure, "By model" shows a small donut of each model's share of Cost, Credits or Tokens (whichever is selected; the top four and Other), when more than one model was used. Each response counts toward the model that wrote it, as in By model of Where it went; Active time can't be split by model, so it has none
  - **Output**: Commits (Git commits with the share by AI, or AI commits when no Git repository could be read), Pushes (from this computer's git reflog, with how many commits they sent) or PRs (pull requests created by AI). Each bar is labeled with its count like the Input chart. Pushes before the oldest push git still keeps (90 days by default) are left out rather than counted as 0
  - **Unit cost per output**: two switches, the measure (Cost, Credits or Tokens) and what it is divided by (Commits, Pushes, PRs or 100 AI lines, the lines the agents' edit tools added and removed). Commits with Cost or Tokens is Claude Code's cost or tokens per AI commit when AI commits are recorded (only Claude Code records which commits it ran); otherwise, and always with Credits, it is the period's whole total per Git commit (the same Git commits as in Output), and the figure's name says which ("Claude Code estimated cost per AI commit" or "Kiro credits per Git commit"). Per Git commit, per push and per PR divide the period's whole total of the measure, because a Git commit, a push or a pull request can't be split into the part AI did; the note under the value says so. PRs counts only pull requests an agent recorded creating (Claude Code), so with Kiro or Codex alone it is not offered; kiroku doesn't guess pull requests from commit subjects. What it is divided by shows only the choices with a figure for the measure picked. Each names what it divides and shows "numerator ÷ denominator" under the value
  - **Unit cost per input**: the same two switches, with what it is divided by being Session hour, Active day (the days the sessions ran), Session or Prompt. Each divides only by the sessions that record what it divides, and its "ƒx" says so (an agent that records credits but no tokens does not dilute cost per hour; per session hour uses each session's own active time, so overlapping sessions each count and the hours can exceed Active time)
  - Under each unit cost's value, one line says how it went: below or above typical when the value is outside the usual range by 10% of the range's edge or more (or far outside it), "Close to usual (slightly below/above)" when it is outside by less than that (the "ƒx" says so), otherwise as usual, with the reason (the lowest or highest of recent periods, several periods in a row, or the typical range). A second line appears only when there is something to act on: on the lower side, what was different (sessions shorter or with fewer prompts than usual, by a quarter or more); on the higher side, a likely cause (the same session habits, or a Worth a look item of the period that opens its dialog), or else a link to the sessions that used the most. These are rules, not AI
  - A small mark under a figure without a verdict says where it falls against your usual range

  - A value far outside your usual range (beyond 75th pct + 1.5×spread or 25th pct − 1.5×spread, the same rule as "far above") is shown in amber with a small ↑ or ↓ next to it (no words; a screen reader reads "Far above usual" or "Far below usual", which is also the arrow's tooltip), in the panels and in the Breakdown cards.   - In a period in progress, every amount and count also shows its month-end (or week-end) estimate at the current pace on the same row as the value, such as "$6.87 So far ≈ $16.03 End-of-week estimate" (the estimate a size smaller, on the same baseline; on a narrow screen it wraps to the next line), and the chart draws it: in Input and Output as the bar so far with a lighter dashed bar on top up to the estimate.   - A small red triangle just under the x axis of Input marks when you hit a usage limit (one per period at the first hit, with ×n when there were more; touch it for the times and when each reset)
  - One legend per panel, under its chart, explains the charts: the middle half of your past periods as a shaded band with its median dashed, and the period shown as a bar in Input and Output (with the dashed bar of its end-of-period estimate in a period in progress) or as a dot in the unit cost panels.   - A note under the value gives the change from the previous period: in percent for amounts and rates, and as a difference for counts (commits, pushes, pull requests). ### Outputs

Numbers shown next to costs such as time and tokens, to check whether your usage led to work that left a trace. They count how much was produced (outputs), not its value or productivity.

Outputs come in two parts that are counted differently, so the view keeps them apart everywhere: under their own headings and marks in the summary and in session details, and never added together. A unit cost divides by one part only: per AI commit, or per 100 AI-edited lines.

- **Git**: what reached your repositories, read with your local `git`, and the pull requests and commits AI ran with tools
- **AI edits**: files and lines the agents changed with their edit tools, read from history (Claude Code, Codex and Kiro), whether or not the changes were committed. Lines are an estimate: for each edit, the lines left after dropping the lines that stayed the same at the start and end

**Git**

- **Git commits** are counted by reading the repositories agents worked in (each session's working directory) with your local `git`, counting your own commits (`git config user.email`; in repositories without `user.email`, everyone's commits are counted). Commits made by hand are included. Commits whose time matches (within 2 minutes of when the tool returned) a commit an agent ran with a tool are counted as "By AI". Each run is matched to the one nearest commit only. A git worktree is treated as the same repository as its main checkout. kiroku never fetches from a remote, so in a partial clone (`git clone --filter=...`), commits whose files aren't on your computer are listed without changed lines and files. The calendar shows them as commit marks and short-hash badges (filled ones were run by AI). They are not read where the `git` command is unavailable
- Everything else counts only what AI ran with tools and succeeded (currently Claude Code only)

| AI-added lines that reached a commit | In Claude Code sessions that started in the period, the lines AI added in its edits that ended up in that session's own AI commits, as a share of all lines it added (capped per session at what it edited) | How much of what AI wrote was kept rather than rewritten or dropped | Lines you committed by hand later, or that were rewritten in another session. Only Claude Code records which commits it ran | When it is low, check sessions that edited a lot but committed little: the plan may have changed midway |
| Estimated cost per 100 AI-edited lines | Estimated cost ÷ lines edited by AI × 100, both from the sessions that started in the period, are from an agent that records edits and record tokens. Commits made by hand do not count, and changes that were never committed do | Roughly how heavy each change AI wrote was, without depending on git or on how often you commit | What reached a commit, or the value of the changes. Rewriting the same lines counts each time, and sessions without edits (research, review) still add cost | Read it next to cost per commit: if per-line cost is flat but per-commit cost rises, the same work is reaching fewer commits |
| Kiro credits per 100 AI-edited lines | Kiro credits ÷ lines edited by AI × 100, from the sessions that record both (Kiro IDE / CLI). It does not depend on commits you made by hand | Roughly how many credits each change Kiro wrote took | What reached a commit, or the value of the changes. Sessions without edits (research, review) still add credits | Compare with the Kiro credits trend: credits going up while edited lines stay flat means more credits per change |
| Tokens per 100 AI-edited lines | Tokens ÷ lines edited by AI × 100, on the same basis as estimated cost per 100 AI-edited lines | Roughly how much context each change AI wrote took, whatever the model's price | What reached a commit, or the value of the changes | If it rises while cost per 100 AI-edited lines stays flat, the work moved to a cheaper model; if both rise, sessions carry more context per change |

Session details show the same two parts for that session under **Output**: **Git** (commits made during the session, with the share by AI where the agent records it, and pull requests created) and **AI edits** (files and lines edited, and the credits or estimated cost per 100 AI-edited lines).

### Context windows

"Long conversations" compares a conversation's peak input with the model's context window. Claude Code does not record the window, so kiroku works it out:

- The input of each response (new input plus cache reads and writes; for a response that made several calls with the advisor tool, its largest single call) divided by the model's context window, from a table in kiroku (`ContextWindows` in `internal/core/context.go`, from the official docs). Models not in the table get no value
- On the Anthropic API, Fable 5.2, Mythos 5.2, Fable 5.1, Fable 5, Sonnet 5 and later, Opus 4.7 and later and Haiku 5.5 have 1M tokens
- Opus 4.6 and Sonnet 4.6 have 200K unless you picked their `[1m]` variant, which the history doesn't show, so kiroku assumes 200K and switches to 1M for a model once a response read more than 200K
- With `CLAUDE_CODE_DISABLE_1M_CONTEXT`, or on Amazon Bedrock, Google Cloud and Microsoft Foundry with Claude Code before v2.1.287, the window may be 200K where kiroku assumes 1M, so the value reads low there

Codex records its own window.

Times are calculated in your computer's time zone. All numbers are rough estimates from history. When there is no data, "Unknown" is shown instead of 0. When none of the agents used in the period records something (for example, Kiro IDE / CLI (V3) records no usage limit hits), the metric shows "Not recorded" and "… doesn't record this" instead of 0; session details show "Not recorded in … history" under "Files edited by AI". Tokens, estimated cost and total AI run time are rough measures of usage; they do not show productivity or time saved.

> These numbers are for reflecting on how you work. Don't use them to compare or evaluate people.

### History retention

Some agents delete old history automatically. Deleted history cannot be shown by kiroku and cannot be recovered, so set this up early if you want to look back further. In the view, "Data sources" shows the oldest record for each agent, and while Claude Code or Kiro Crew is still on its 30-day default, it is flagged there (with a ⚠ on the folded section) with a link to the docs and the two ways to keep the history: the setting and the file to put it in, or keeping a copy in kiroku's folder ("Keep a copy in this folder"), which it names. `kiroku serve --check` shows the same under "Keeping history".

| Agent | Deletes automatically? | Setting |
|---|---|---|
| Claude Code | **Yes.** By default it silently deletes conversation history older than 30 days at startup. Since v2.1.248, sessions you started or last continued in Claude Desktop or Cowork are kept at any age unless `desktopSessionCleanupPeriodDays` is set (or your organization's managed settings set `cleanupPeriodDays`) | [`cleanupPeriodDays`](https://code.claude.com/docs/en/settings-reference#cleanupperioddays) in `~/.claude/settings.json` (days, a whole number, minimum 1; `0` fails validation, so use a large value such as `3650` for long retention) |
| Kiro Crew | **Yes.** By default it deletes conversation records moved to `sessions/archive/` (and the logs of closed sessions) that are older than 30 days. It checks whenever it moves records there, at most once an hour | Crew's [`session.archive_retention_days`](https://github.com/kirodotdev/kirocrew/blob/main/src/kiro_crew/docs/configuration.md) in `~/.kiro/crew/config.local.json` (or `config.json`; under `KIROCREW_HOME` if set). Days; `-1` or `null` turns the cleanup off, and `0` deletes all archived records at the next cleanup |
| Kiro IDE / CLI (V3), Kiro CLI (V2), Codex | Their official docs do not describe age-based automatic deletion (manual cleanup exists) | — |

Example for Claude Code:

```json
{
  "cleanupPeriodDays": 3650
}
```

kiroku reads your user settings (`~/.claude/settings.json`, or under `CLAUDE_CONFIG_DIR` if set) and your organization's [managed settings](https://code.claude.com/docs/en/managed-settings), which win over your own (the files it reads are listed in [sources.md](sources.md#history-retention)).

- If `cleanupPeriodDays` in your settings is not a whole number of 1 or more (such as `0` or `"30"`), or a settings file exists but can't be read or parsed, Claude Code pauses its cleanup and deletes nothing until you fix it (unless the managed settings set `cleanupPeriodDays`), so kiroku shows no notice. Claude Code also pauses for other settings errors when `cleanupPeriodDays` is set; kiroku can't check that
- If the period is set in project settings, in server-managed settings from claude.ai or by MDM (a macOS profile or the Windows registry), the notice may not match the actual period
- kiroku shows one period for all Claude Code history; it doesn't single out Claude Desktop and Cowork sessions, which Claude Code keeps longer as described above

Example for Kiro Crew (`~/.kiro/crew/config.local.json`; its values win over `config.json`. If the file already has a `"session"` object, add the key inside it):

```json
{
  "session": {
    "archive_retention_days": 3650
  }
}
```

`-1` instead of `3650` turns Crew's cleanup off, and kiroku then shows no retention for it. With `0`, Crew deletes every archived record at its next cleanup (the next time it moves records to `sessions/archive/`), so "Data sources" and `kiroku serve --check` say so (unless `kiroku serve --archive` keeps a copy).

kiroku reads `config.json` and `config.local.json` the same way Crew does. A period of exactly 30 counts as Crew's default, so it is still flagged ([why](sources.md#history-retention)).

### Keep a copy of history in kiroku

If you'd rather not change the setting, kiroku can keep a copy of the history instead. It is off until you turn it on.

- Run `kiroku serve --archive on`, or press "Keep a copy in this folder" under "Data sources" in the `kiroku serve` view (the folder is named next to it; Data sources stays open and the row then says kiroku keeps a copy). kiroku saves the current history right away, then saves new and appended history each time `kiroku serve` reloads
- Only history from agents that delete it automatically is saved (Claude Code conversations, and Kiro Crew's `sessions/archive/`). Each file is compressed with zstd and kept in the same layout as the original
- When the original conversation is deleted, kiroku shows it from the copy. "Data sources" shows how many conversations came from the copy, and the number and size of the saved files. Claude Code conversations shown from the copy have no "Resume" command (Claude Code no longer has them)
- The copies live in `~/.local/share/kiroku/archive` on Linux (under `XDG_DATA_HOME` if set), `~/Library/Application Support/kiroku/archive` on macOS and `%LocalAppData%\kiroku\archive` on Windows. Change it with `--archive-dir` or `KIROKU_ARCHIVE_DIR`. Copies stay on this computer and are never sent anywhere
- `kiroku serve --archive off` stops saving and asks whether to delete the copies already kept (only if you answer `y` in a terminal). It deletes only the compressed copies (`.zst` files) kiroku saved, and folders left empty; other files in the folder stay. It only offers this in a folder where `kiroku serve --archive on` was run, so a mistyped `--archive-dir` never deletes anything. If you keep them, kiroku still shows them
- History deleted while kiroku is not opened cannot be saved, so open kiroku at least once before the period ends. The conversations exist in one more place, so even conversations you deleted on purpose remain in kiroku's copy, and so does the text of Kiro Crew's incognito and temporary conversations that Crew moved to `sessions/archive/` (kiroku does not show it; see the note on Kiro Crew under "Notes")

### Open kiroku in a window of its own

In Chrome or Edge, open the view with `kiroku serve` and choose "Install kiroku" in the address bar or the browser's menu (Edge: Apps → Install this site as an app). kiroku then opens in its own window, with its icon in the Dock or taskbar, like a desktop app.

- The app window shows the view of `kiroku serve` at the same address, with the key your browser already has. If `kiroku serve` isn't running, it shows the browser's "can't connect" page
- `localhost:8484` and `127.0.0.1:8484` are different apps; install from the address you use. After changing the port, install again
- Nothing is kept for offline use: kiroku installs no service worker, so the browser keeps no copy of your history
- Safari's "Add to Dock" is not tested yet; a web app there has its own site data and may show "Open kiroku with its key"
- To remove it, use the app window's menu (Uninstall) or the browser's app list

## The key of kiroku serve

`127.0.0.1` keeps other computers out, but not other users of the same computer (a shared server you log in to with SSH, for example): any of them could open `http://localhost:8484/`. So `kiroku serve` shows your history only to a browser that has its key.

- The key is made the first time `kiroku serve` runs and kept in `serve-key` in kiroku's settings folder (`~/.config/kiroku` on Linux, `~/Library/Application Support/kiroku` on macOS, `%AppData%\kiroku` on Windows, or `$KIROKU_CONFIG_DIR`), readable only by you. Every `kiroku serve` of yours uses the same key
- `kiroku serve` (unless `--no-open`) opens the view with a one-time code (`?code=`), not the key: browsers keep every address they open in their history, and sync it when history sync is on. The code works once, within 10 minutes, and `kiroku serve` hands the key to the page it opens. Running `kiroku serve` again while it is running opens the running view the same way. It doesn't pass the address to the browser on its command line (other users can see that); it opens `open.html` in the same folder, readable only by you, which forwards to it
- An address with `?key=` (made by versions before v0.38.2) no longer opens kiroku (run `kiroku serve` instead). It may still be in your browser's history with the key in it: delete those entries, or change the key (below)
- The browser then keeps the key in its site data (`localStorage`) for that address and port, and the address without the key works, including bookmarks: the page asks `kiroku serve` for your history with the key. Another browser, a private window, a browser whose site data was cleared, or the same port under another name (`127.0.0.1` instead of `localhost`) shows "Open kiroku with its key"; run `kiroku serve` again
- After upgrading from a version that kept the key in a cookie, run `kiroku serve` once in each browser; kiroku removes the old cookie (why it no longer uses one is in [SECURITY.md](../SECURITY.md))
- kiroku no longer gives the key to a browser on another device: kiroku 5.0 removed `--print`, which printed a one-time address for one
- To change the key, stop `kiroku serve`, delete `serve-key` and start it again. Browsers then need `kiroku serve` run again while it runs

## Uninstall

1. If you used `kiroku autostart on` in kiroku 4, run `kiroku autostart` once. In kiroku 5 it only stops the `kiroku serve` that login item started and removes the item
2. If you turned on `kiroku serve --archive`, run `kiroku serve --archive off` and answer `y` to delete the copies of history it kept. Or delete the folder yourself: `kiroku serve --archive` shows where it is (by default `~/.local/share/kiroku` on Linux, `~/Library/Application Support/kiroku` on macOS, `%LocalAppData%\kiroku` on Windows)
3. Delete kiroku's settings folder, which holds the key of `kiroku serve` (`~/.config/kiroku` on Linux, `~/Library/Application Support/kiroku` on macOS, `%AppData%\kiroku` on Windows, or `$KIROKU_CONFIG_DIR`)
4. On macOS, if you used autostart in kiroku 4, delete the log it wrote, `~/Library/Logs/kiroku.log` (`kiroku autostart` leaves it)
5. Delete the binary: `rm "$(command -v kiroku)"` (with `sudo` if it is in `/usr/local/bin`)

Apart from these, kiroku keeps nothing of its own; view settings are stored in your browser.

## Notes

- In a terminal, kiroku colours its output: green `✓` for what is fine, yellow `!` for what needs attention, red for what failed, dim for notes you can skip, and bold for the commands and addresses you are meant to use. Output that goes to a pipe or a file is plain, and so is a terminal where `NO_COLOR` is set (see [no-color.org](https://no-color.org/)) or `TERM=dumb`. `install.sh` follows the same rules
- Kiro Crew conversations you held in incognito or temporary mode are shown with counts and times only (time span, prompts, turns, model, tools, credits, tokens and cost), titled "Kiro Crew private conversation". Their prompts, replies, title and files are not in the view or the prompts kiroku copies for an AI, and neither are their copies in the Kiro CLI SQLite, Codex and Claude Code history that kiroku can match (also with `--sources codex` or `--sources claude`). Git commits made during their time span are still listed, since they come from the repository. Some copies can't be matched and are shown in full, such as a temporary subagent's own session; the cases are in [sources.md](sources.md#kiro-crew). `kiroku serve --archive` copies Crew's `sessions/archive/` files as they are, so its copy still holds their text
- By default, `kiroku serve` can be reached only from your own computer, and only by browsers that have its key (see "[The key of kiroku serve](#the-key-of-kiroku-serve)"). If you expose it, as in `kiroku serve 0.0.0.0:8484`, devices on the same network can reach it, and anyone who gets the address with the key can view your history. See [SECURITY.md](../SECURITY.md) for how it still guards against other sites
