# How histories are read

This page summarizes where kiroku reads each agent's history from and how. The list of locations is in [the guide's "Histories read"](guide.md#histories-read). Every adapter converts what it reads into the common session shape (`Builder` in `internal/core`). History lines longer than 64 MiB are skipped and the file is listed as unreadable in "Data sources", and compressed history (`.zst`) is read with a memory limit.

## Claude Code

`~/.claude/projects/*/*.jsonl` (or `projects` under `CLAUDE_CONFIG_DIR` when it is set). `internal/source/claude.go`

- Previous transcripts that Claude Code set aside instead of overwriting (`<session>.orphaned-<timestamp>-<suffix>.jsonl`; they don't appear in Claude Code's session picker) are not read, so a conversation is not counted twice. The same applies to their `kiroku archive` copies. `<session>.jsonl.superseded-<timestamp>` does not end in `.jsonl` and is not read either

- Timestamps are per message. Prompts are `type: "user"` lines; the AI's activity is `assistant` lines
- A prompt sent while the AI is working is recorded only as a `queued_command` (`origin.kind: "human"`) in a `type: "attachment"` line, not as a `user` line, so it is picked up from there too. Messages from other agents (`peer`) and task notifications (`task-notification`) are not counted as prompts
- `isCompactSummary` lines written when a long conversation is summarized automatically ("This session is being continued…") are not counted as prompts
- Compactions come from `type: "system"` lines with `subtype: "compact_boundary"` (with `compactMetadata.trigger`, `auto` or `manual`, shown in the prompt flow when present; other values are ignored) and from the `isCompactSummary` line written right after. The two are one compaction, so marks within 1 minute count once; summaries from older versions without `compact_boundary` count on their own. Subagent (`isSidechain`) lines and subagent files are not counted. The [Agent SDK](https://code.claude.com/docs/en/agent-sdk/typescript) documents the same event as `compact_boundary` with `compact_metadata.trigger` (`manual` / `auto`) and `pre_tokens`; the transcript writes it in camelCase (`compactMetadata.preTokens`, as read by codeburn)
- The text of `user` lines is classified in `internal/core/kind.go`. Slash commands (`<command-name>` and `<command-args>`) become "/name args" and `<bash-input>` becomes "! command", and both count as prompts the person typed (`kind` is `command` or `shell`). `<system-reminder>` is stripped even when it appears inside the text. Text starting with tags such as `<task-notification>`, `<user-prompt-submit-hook>` or `<local-command-stdout>`, `Caveat:`, `isMeta` lines (such as the expanded text of a slash command), summaries, and `queued_command` entries not sent by a person are not counted as prompts; they are kept in `notes` (kind and first 160 characters, up to 300 per session) and shown in the prompt flow in a different color
- A single response is recorded across several lines, so tokens are grouped by message ID before counting (taking the largest value for each field, including the web search count)
- Web searches (`usage.server_tool_use.web_search_requests`) are priced at $10 per 1,000 in the price-table estimate ([pricing](https://platform.claude.com/docs/en/about-claude/pricing), Web search tool), without the fast-mode or US-only multipliers, which apply to tokens only. Where Claude Code's own `cost-state` record is used, its total already covers everything, so nothing is added
- Peak context usage is computed per response of the main conversation (not subagents): new input plus cache writes and reads, divided by the model's context window from `ContextWindows` in `internal/core/context.go` (matched by the longest model ID prefix, like the price table; models not in it get no value). Opus 4.6 and Sonnet 4.6 count as 200K unless a response read more than that, in which case that model counts as 1M in that session (the `[1m]` variant doesn't show in the history). The window of the model of the largest response is kept in the session (`ctxWindow`) so "Long conversations" can use half of it as its peak threshold
- Cache writes are split into 5-minute and 1-hour writes by `cache_creation.ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens`. Some older versions wrote `cache_creation_input_tokens` as 0 with only that breakdown filled in, so the total is the larger of `cache_creation_input_tokens` and the sum of the breakdown
- Usage limit hits are the messages Claude Code itself writes (`isApiErrorMessage`, model `<synthetic>`) whose text is a usage-limit error: usage caps (`You've hit your session limit`, weekly, Opus and Sonnet limits, older `usage limit reached` / `5-hour limit reached`), spend limits and budgets (`You've hit your monthly spend limit`, `…org's monthly spend limit`, `…team's shared budget`, a gateway's `spend limit reached`) and rate limits (`429`, `rate_limit_error`, `Request rejected (429)`). The server's temporary throttling (`Server is temporarily limiting requests (not your usage limit)`) and `Context limit reached` (the conversation is too long) are not counted. Wording follows [Claude Code's error reference](https://code.claude.com/docs/en/errors)
- When the limit message says when it resets (`· resets 3:45pm`, `∙ resets 3pm`, `resets Mon 12:00am`, `resets 2026-08-09 00:00 UTC`), that text is kept as written (`limitResets`, in the same order as `limits`) and shown with the hit. It usually has no date or time zone, so kiroku does not turn it into a timestamp. Only characters that make up a day, date, clock time or time zone name are taken
- The text the AI wrote back (`text` blocks of `assistant` lines) is kept as that prompt's reply: the last one in the turn, with lines of the same message ID joined. Thinking, tool calls, subagent (`isSidechain`) lines and the messages Claude Code itself writes (`isApiErrorMessage`, model `<synthetic>`) are not replies. The HTML keeps the first 160 characters; `kiroku serve` can show the rest
- Subagents are read from `Task` / `Agent` calls and from `<session>/subagents/agent-*.jsonl` (older versions assign `isSidechain` lines by time)
- Estimated cost follows the `type: "cost-state"` lines Claude Code writes (per-model running totals `modelUsage[].costUSD` since the process started at `startTime`) when they exist. The latest total for each process is used and spread over the responses from process start up to the time of the preceding line, in proportion to kiroku's price-table estimates (by token ratio for models it cannot price). Cost for models with no responses in the history (such as title generation) is added as one entry at that time. Periods with no such record (older versions, or after the last record) are estimated from kiroku's price table
- A model whose `costUSD` is 0 although the history shows it was used is estimated from kiroku's price table instead, so real usage is not shown as $0.00. The `cost-state` line is not documented, so kiroku does not rely on why it is 0. The "(from Claude Code)" note in session details appears only when its record was actually used
- kiroku's price table (`Prices` in `internal/core/usage.go`) follows [Anthropic's pricing page](https://platform.claude.com/docs/en/about-claude/pricing); the numbers it uses are kept in [upstream/anthropic-pricing.md](upstream/anthropic-pricing.md), and a test checks that the two match. A model ID is looked up after removing Bedrock's region and `anthropic.` prefix (`us.anthropic.`, `eu.anthropic.`, `apac.anthropic.`, `global.anthropic.` and so on) and its version marks (a date, Vertex's `@` date, Bedrock's `-v1:0`); `claude-sonnet-4.5` is read as `claude-sonnet-4-5`. A model not in the table under its own ID gets the price of the longest ID it starts with (`claude-opus-5-6` is priced as `claude-opus-5`) and is listed in "Data sources" as "priced as" that ID
- Claude Haiku 5.5 is priced by prompt length (`LongPrices` in `internal/core/usage.go`): a response whose prompt is over 100,000 tokens is priced at the higher rates as a whole (output included). The pricing page doesn't say whether cached tokens count toward the prompt; kiroku counts new input plus cache writes and reads, the whole prompt the model reads. Each response is one message ID in the history, so this applies to every response priced from kiroku's table. Other Claude models have one price for every length

## Kiro IDE

- Replies in the prompt flow come from `assistant` payloads (v1.0 and later), whether their `content` is a string, `text` blocks or nested `content` / `text`; ones with `operationType: "Reasoning"` are the model's thinking, and ones whose content is just `...` are placeholders written while streaming (kiro-history skips them too); neither is a reply. Versions that do not record them simply show no reply
- v1.0 and later: `<hash>/sess_*/session.json` + `messages.jsonl` under `~/.kiro/sessions/` (`~/.kiro` means `KIRO_HOME` when it is set; the same applies below). Per-message timestamps, and credits from `promptTurnSummaries` in `usage_summary`
- v1.0 and later, from shapes seen only in the reference implementations (tolerated when absent): `session_metadata` lines with `key: "contextUsage"` and `value.usagePercentage` (0–100; only codeburn's test data has it) give "Peak context usage", and the length of `usage_summary.requestIds` (only kiro-history reads it) gives "Model requests". Values outside 0–100, and `requestIds` that is not a list, are ignored
- Before v1.0: `<globalStorage>/kiro.kiroagent/workspace-sessions/`. There are no per-message timestamps, so it is shown roughly with start = creation time and end = file modification time. Session IDs in `sessions.json` that contain path separators, `..` or drive names are skipped and reported as unreadable, so nothing outside the history folder is read
- Before v1.0, Kiro adds text of its own to user messages: `<steering-reminder>…</steering-reminder>`, `<EnvironmentContext>…</EnvironmentContext>` and a block starting `## Included Rules` (up to the first paragraph that starts with neither `#` nor whitespace). These are removed the same way kiro-history's `cleanUserContent` does and shown in the prompt flow as system notes; what remains counts as the prompt, and a message with nothing left is not a prompt. kiro-history removes them only from this format, not from v1.0 `messages.jsonl` or Kiro CLI, so kiroku does the same
- Before v1.0, credits and models come from the execution files next to `workspace-sessions` (the layout follows codeburn's `parseModernExecution` and its tests; there is no official description): `<globalStorage>/kiro.kiroagent/<32-hex workspace>/<session>/<execution ID without extension>`, a JSON object with `executionId`, `chatSessionId` or `sessionId`, `startTime` / `endTime` (milliseconds; also under `metadata`), `modelId` (or `metadata.modelId`) and `usageSummary[]` (`usage` in credits, with `unit`; entries whose `unit` is not credits are not counted). An execution belongs to a conversation when the conversation's `history[]` has its `executionId`, or when its `chatSessionId` / `sessionId` is the conversation's `sessionId`. Each execution is a turn with its credits at its end time and its model (the conversation's `selectedModel` when the file has none); a prompt takes the start time of the first linked execution after it, and keeps the creation time otherwise. Conversations without execution files count `selectedModel` once. Files listing executions (`{"executions": […]}`), files that are not JSON, names with an extension or starting with `.`, folders whose name is not 32 hex digits, symbolic links (files or folders) and files over 64 MiB are skipped. Paths are never built from history content; IDs inside the files are only used to link them. Executions that belong to no listed conversation are not shown
- Compactions are not counted: neither format has a marker kiroku can rely on (the formats are not documented, and the reference implementations read none)

`internal/source/kiro.go`

## Kiro CLI

`~/.kiro/sessions/cli/<id>.json` (metadata) + `<id>.jsonl` (conversation). `internal/source/kiro.go`

- A conversation whose `.jsonl` is missing is still shown from its metadata (title, times, credits), without prompts; the missing file is not reported as unreadable. The same holds for a Kiro IDE `messages.jsonl`
- Credits come from `session_state.conversation_metadata.user_turn_metadatas[].metering_usage` (the `value` where `unit` is `credit`)
- Replies in the prompt flow come from the `text` content of `AssistantMessage` lines (new format; these lines carry no timestamp, so a reply is placed at the end of its turn, `user_turn_metadatas[].end_timestamp`, or at its prompt's time when that is missing) and from `assistant.Response` / `assistant.ToolUse` `content` (SQLite; timed by `stream_end_timestamp_ms`)
- Older versions use SQLite (`conversations` / `conversations_v2` in `data.sqlite3`). `internal/source/qstore.go`
- The same conversation can appear in both the new format and SQLite. For a given conversation ID, only the new format is counted (because it has credits). The number left out appears in "Data sources"
- The SQLite history has no tokens or credits, so it is not included in estimated cost or credits
- The new format has no compaction marker kiroku can rely on (the format is not documented and the reference implementations don't read one), so Kiro CLI compactions are counted only from SQLite (see Amazon Q Developer CLI)

## Kiro Crew

`~/.kiro/crew` (or `KIROCREW_HOME` when it is set, with a leading `~` expanded and a filesystem root or system folder such as `/etc` ignored, as Crew does). Crew does not follow `KIRO_HOME` (that moves only kiro-cli's own history), so neither does kiroku. `internal/source/crew.go`

- Crew runs kiro-cli over ACP, so the conversations themselves are recorded in the Kiro CLI history. kiroku counts them there and marks the conversations listed in `session_map.json` and `subagents/*/state.json` as "Kiro Crew", with Crew's title (for a subagent, the agent name and the prompt)
- Conversations run from the Crew dashboard may not have their credits recorded in the kiro-cli history. kiroku also reads the usage records Crew writes every turn (`_type: "tokens"` lines in `usage/tokens/<date>.jsonl`)
- In usage records, the `slot` of a dashboard conversation is recorded as `chat-<sequence>-<UNIX seconds>`. Conversation keys (in `session_map.json` and the conversation log file names) are `dashboard:chat-…`, so they are normalized with the same rule as Crew's `spend_key_for_slot` before matching
- To avoid counting a conversation twice, whichever of the kiro-cli record and the Crew record is larger is used for each conversation
- Records that do not match a kiro-cli conversation become "Kiro Crew" sessions: Crew's background work (`slot: "_bg"`) per day, memory consolidation per memory store and day (Crew gives every run its own `memory-consolidation:<store>:<random id>` slot, so each run would otherwise be a session of its own), and dashboard chats per conversation
- A subagent's usage records use its own slot, not its parent's key: the `conversation_key` in `subagents/<id>/state.json` (written only for subagents Crew keeps), or else `subagent:<id>` (`subagent_manager/run.py`). These records are matched to the subagent's kiro-cli conversation like any other conversation's. Crew deletes the kiro-cli files of subagents it does not keep, so for those only the usage records remain. When several continued runs share one slot, its records go to one of their conversations only
- A subagent is shown inside its parent's session, as Claude Code and Codex subagents are: the parent is the conversation whose key is the `parent_session` in `subagents/<id>/state.json`, whether it is a kiro-cli conversation, a usage-only session or a log-only session. The subagent appears in the parent's details with its agent name, prompt, start and end, model, tool calls, tokens and cost; its credits, edited files and Crew metrics ("Conversations run from Crew", "Of which subagents") are added to the parent's, so totals are the same as before. The times the subagent was working count as AI activity in the parent session, so they are part of its active time and not a wait. The prompt Crew sent the subagent is not counted as a prompt you typed. When the parent can't be found (its records are gone), the subagent stays a "Kiro Crew" session of its own, titled with its agent name and prompt
- Crew's conversation logs (`sessions/<conversation key>.jsonl`; the first line is metadata, then `role`, `content`, `ts` and `tools` from the second line) are read too. For conversations whose prompts are not in the kiro-cli history (such as those run from the dashboard) and conversations that do not match a kiro-cli conversation, the prompt flow (including the `assistant` lines as replies), times and tools used are filled in from here. A conversation that has only a conversation log, with neither usage records nor a kiro-cli conversation, also becomes a "Kiro Crew" session
- A `user` line is not always something a person typed: Crew also writes scheduled runs (`# Cron Run: …`), Issue Radar wakes, the task runner and auto-go as `user` lines, and marks the lines a person wrote with `meta.human: true` (`HUMAN_TURN_META_KEY` in `history.py`, an allowlist). From the first marked line of a log on, only marked lines count as prompts, and the other `user` lines are shown as messages sent by another agent or a schedule. Lines before that (logs written before Crew had the marker) can't be told apart, so every `user` line there counts as a prompt
- Forking a conversation (`dashboard/chat_fork.py`) copies the parent's lines into a new log with their original `ts` and `meta`, and records the parent's key as `forked_from` in the new log's metadata, whose `created_at` is the time of the fork. Lines of a fork whose `ts` is before `created_at` are those copies and are skipped, since the parent is counted on its own. A fork that has only copied lines is not a session. `ts` and `created_at` are used rather than matching `meta.mid` with the parent because copied lines without a `mid` get a new one, and the parent's log may have been rotated, archived or deleted. A fork whose metadata has no `created_at` can't be told apart and is read whole
- Older lines that overflow a conversation log are moved to `sessions/archive/<name>__<datetime>.jsonl` (how long they are kept is set by Crew's `session.archive_retention_days`, 30 days by default, or 7 days if Crew cannot load its configuration; see [History retention](#history-retention)), so those are also read, oldest first, while they exist. For a conversation whose log is gone because it was closed or expired, the session comes from usage records only and has no prompt flow
- Crew does not delete its usage records (its own dashboard shows only the last 30 days of them), so kiroku reads every day that is still in `usage/tokens/`
- Compactions are not counted: Crew uses the compaction events its backend reports only while a turn runs and does not keep them, and `compacted_at` in a conversation log's metadata marks Crew rewriting its own log (and only the latest time). The conversation itself is kiro-cli's, whose JSON history has no compaction marker kiroku can rely on
- Usage records are written by Crew's `_build_token_record` (`dashboard/handlers/usage.py`): `provider`, `model`, `input`, `output`, `cache_create`, `cache_read`, `cost` (USD), `credits`, `turns`, `duration_ms`, `surface`, `agent`, `context_used`, `context_window` and `stop_reason`. Each backend fills what it bills in (`TurnUsage` in `acp/types.py`): kiro-cli only credits, Claude Code and other ACP backends tokens and `cost`. The four token fields don't overlap (Crew's own total adds them up), so they map to input, output, cache writes and cache reads. `cost` is the change in the backend's running session total, so it lands on the turn where it arrived; when any turn of a conversation has a cost, turns without one count as $0, and a conversation without any cost is estimated from the price table (models not in it are listed as unpriced). Negative or non-numeric values count as 0
- The row's `provider` is Crew's seam (`acp` for every ACP backend, `claude_code` for the Claude Code seam), and `session_map.json` keeps the backend label of each conversation (`provider`: absent or `acp` for kiro-cli, `claude_code`, `codex`, `kas`, `goose` and others). Tokens and cost are not added for rows whose seam or label is `claude_code`, or whose label is `codex`: Claude Code (Crew runs it through claude-agent-acp) and Codex write their own history, which kiroku reads, and Crew's session id can't be shown to match those histories' ids from the public sources (claude-agent-acp is not among them), so adding the rows could count the same tokens twice. Their turns, times, credits and models still count, and "Data sources" gives the number of turns left out. A Codex conversation that is no longer in `session_map.json` can't be told apart (its rows say `acp`), so its tokens may be counted twice
- "Peak context usage" is the largest `context_used` ÷ `context_window` (rows without a window are skipped, as in Crew's own context view; values over 100% count as 100%), and "Turns that did not end normally" counts rows whose `stop_reason` is set and is not `end_turn` (for example `cancelled`, `refusal`, `max_tokens` or Crew's `error: tool stall`). Crew writes no row for a turn that billed nothing, so such turns are not in either. Both are read from every row, including those of kiro-cli conversations

## Amazon Q Developer CLI

`amazon-q/data.sqlite3` (location in the table in [guide.md](guide.md#histories-read)). Same format as older Kiro CLI versions. `internal/source/qstore.go`

These points apply to both Amazon Q and Kiro CLI (SQLite):

- Lines the CLI writes on your behalf are not counted as prompts: `CancelledToolUses` with "The user interrupted the tool execution." (Ctrl+C during a tool run) counts as an interruption, and the text sent when you deny a tool with "n", the summary request of `--resume` without input, and the messages after a response timeout or history overflow are shown as "Added by the agent". Any other text you type when declining a tool is a prompt
- Turns that return tool results have no `user.timestamp`, so `request_metadata.request_start_timestamp_ms` is used
- Also not prompts: the reason sent when the CLI itself rejects a tool whose arguments are forbidden by its settings ("Tool use with … was rejected because the arguments supplied were forbidden") and the request `/todos resume` sends (starting with "[SYSTEM NOTE: This is an automated request, not from the user]") are shown as "Added by the agent", and so are the user and assistant pairs an MCP prompt adds with `/prompts get` (they have neither `user.timestamp` nor `request_metadata`; their reply is not shown as a reply). The oldest `[user, assistant]` format is still read as prompts
- The same conversation can be stored under several folders (for example after `/load`). Only the most recently saved copy is read (`conversations_v2` by `updated_at`, `conversations` by the order rows were saved)
- Rows that can't be read are skipped and reported in "Data sources"
- The model is counted only for history entries with `request_metadata` (an actual request). Interruptions, MCP `/prompts` lines and other lines the CLI adds have none. The oldest `[user, assistant]` format has no `request_metadata` at all, so its entries count except interruptions
- `response_size` is in bytes (the reply plus the tool input JSON)
- Compactions: `/compact`, and the automatic compaction when the context overflows, keep the summary in `latest_summary` as `[summary, request_metadata]` (`replace_history_with_summary` in `conversation.rs`), and that request's `message_meta_tags` contain `Compact` (`compact_history` in `mod.rs`). Its `stream_end_timestamp_ms` (or `request_start_timestamp_ms`) is the time. A new compaction overwrites the previous summary and drops the turns before it (`history.drain`), and `/clear` removes it, so only the latest compaction of a conversation can be counted. The oldest format, a summary string without `request_metadata`, has no time and is not counted
- "Context window" is `model_info.context_window_tokens` (200,000 when it is missing, as in the CLI's `context_window_tokens`). "Peak context usage (estimate)" uses the CLI's own estimate (`token_counter.rs`: bytes ÷ 4, rounded to tens of tokens) over the stored history, entry by entry: the user message (`additional_context`, the prompt and tool results, JSON values counted as in `calculate_value_char_count`) and the reply (text and tool input values), plus the last context message length (`context_message_length`, with the fixed reply the CLI adds to it). It is the largest share of the window, capped at 100%. It leaves out tool definitions and anything `/compact` or `/clear` removed from the stored history, so it can be lower than what the CLI showed

## Codex CLI

`~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl` (and `.jsonl.zst`) and `archived_sessions/` (under `CODEX_HOME` when it is set). `internal/source/codex.go`

- Prompts come from `user_message` events. Rollouts with `history_mode: "paginated"` write them as `item_completed` events instead, whose item is a `TurnItem` tagged with its Rust name (`"type": "UserMessage"` with `content: [{"type": "text", "text": …}, …]`); only the text parts are kept. Older rollouts with neither use `message` items whose role is `user`; there, the context Codex injects is not counted as a prompt: text that starts with a tag (`<environment_context>`, `<user_instructions>`, `<turn_aborted>`, `<subagent_notification>`, `<user_shell_command>` and others) AGENTS.md instructions (text starting with `# AGENTS.md instructions`, the shape of `UserInstructions` in `core/src/context/user_instructions.rs`), and the untagged notices older versions added as user messages (`core/src/context/contextual_user_message.rs`): the list of plugins that are available but not installed, and the warnings about the unified exec process limit, `apply_patch` requested through `exec_command`, and an account flagged for high-risk cyber activity
- Input sent by a scheduled heartbeat is recorded like a typed prompt (`user_message`, or `UserMessage`), but the `message` item with role `user` written just before it carries `internal_chat_message_metadata_passthrough.content_item_kinds: ["user.heartbeat"]` (`UserInputOrigin::from_message` in `history/src/heartbeat.rs`). Such input is shown as added by a schedule, not counted as a prompt, and the replies of its turn are not attached to the previous prompt. The turn's `turn_attribution.turn_trigger` is not used: a prompt you type while a heartbeat turn runs is yours
- Replies in the prompt flow come from `agent_message` events, `item_completed` items of type `AgentMessage` (`content: [{"type": "Text", "text": …}]`) and `message` items whose role is `assistant`. `developer` messages (instructions Codex adds) are not replies
- The same token values are written repeatedly, so each is counted once. Newer versions write each response twice, a `token_usage_record` followed by a `token_count`, so from a file's first `token_usage_record` on only the records are used. A session started on an older version and resumed on a newer one has both in the same file (resuming appends to it): usage before the first record comes from `token_count`, and from the records after it. Context usage always comes from `token_count`. Each response is one "Responses" (model request); in the oldest rollouts, whose `token_count` has no `last_token_usage`, each `token_count` whose total grew is one. `cached_input_tokens` and `cache_write_input_tokens` are both part of `input_tokens` (the Responses API's `input_tokens_details`), so both are taken out of input
- Subagent and fork files copy the parent's history right after their own `session_meta`, with the time of copying, so the copy can't be told apart by time. It is skipped by what marks its end: in paginated subagent files, lines whose `ordinal` is below `session_meta.subagent_history_start_ordinal`; in other subagent and fork files (`source.subagent` or `forked_from_id`), the lines before the first `thread_settings_applied` event carrying the file's own thread ID, which Codex writes together with the copy (copied ones keep the parent's ID). Older versions write neither, so for them, and when that event was only written later on resume, lines dated before the file's `session_meta` are not counted, as before. Subagents are grouped under "Subagents" in the parent session
- Usage limit hits come from two places. A `token_count` event whose `rate_limits.rate_limit_reached_type` is set (Codex sets it only from a 429 `usage_limit_reached` response); Codex writes its latest snapshot again in later `token_count` events, so the same snapshot written again is not counted twice. And a turn that stopped on a limit: `task_complete` (also read as `turn_complete`) whose `error.codex_error_info` is `usage_limit_exceeded` (usage caps, an exhausted quota, or a plan that does not include Codex) or `rate_limit_exceeded` (an API rate limit; Codex also maps the server's `slow_down` to it, and the two can't be told apart). `context_window_exceeded` (the conversation is too long), `session_budget_exceeded` (Codex's own budget) and other errors are not counted. A subagent's hits count for the parent session
- Interruptions are `turn_aborted` events with `reason: "interrupted"` (you stopped the turn). `replaced`, `review_ended` and `budget_limited` are not counted
- Compactions are `type: "compacted"` lines. Every compaction (local, remote including remote compaction v2, and token-budget compaction) writes one through `replace_compacted_history`, and the rollout policy (`rollout/src/policy.rs`) persists it in every history mode. The `context_compacted` event (legacy rollouts only) and the `item_completed` item of type `ContextCompaction` mark the same compaction and are not counted. A fork or subagent file starts with the parent's copied lines, `compacted` included; those are skipped with the rest of the copy. A subagent's own compactions are not added to its parent session. Codex does not record whether a compaction was automatic or manual
- Limit usage comes from `token_count.rate_limits`: `primary` and `secondary`, each with `used_percent` and `window_minutes`. Each window is shown by its length the way Codex names it (5-hour, daily, weekly, monthly, annual, within 5%); a window without `window_minutes`, or of another length, is shown as "Peak rate-limit usage" (primary) or "Peak secondary rate-limit usage". Only snapshots whose `limit_id` is `codex`, or that have none (older versions), are used; other IDs are separate per-model limits. When a response's headers carry several limit families, Codex parses them all (`parse_all_rate_limits` in `codex-api/src/rate_limits.rs`) and keeps only the last one as its latest snapshot (`set_rate_limits` replaces `primary` and `secondary`), so the `token_count` written for that response may hold another family's `limit_id`. Such snapshots are skipped, so the 5-hour and weekly usage can be missing for that response; the history has no way to recover it
- Context usage is worked out the way Codex shows it: `(last_token_usage.total_tokens - 12000) / (model_context_window - 12000)`, kept between 0 and 100% (12,000 is Codex's `BASELINE_TOKENS`, what is always in the context). When the context overflows, Codex writes a `token_count` filled to the window (`total_token_usage` holds only `total_tokens` equal to the window, the rest 0); it counts as 100%, and not as a response
- Time to first token and turn duration are the medians of `time_to_first_token_ms` and `duration_ms` in `task_complete`, from turns that finished without `error`. Older versions don't write them, so they are not shown for those
- Tool calls are `function_call`, `custom_tool_call`, `local_shell_call` (shown as `local_shell`), `web_search_call` (`web_search`), `tool_search_call` (`tool_search`) and `image_generation_call` (`image_generation`) items, all of which the rollout policy persists
- `thread/revert` (paginated history only, `thread-store/src/local/revert_thread.rs`) writes a new rollout file for the same thread, named `rollout-<time>-<thread ID>_<rollout ID>.jsonl`, whose `session_meta` keeps the thread ID and points at the retained prefix of the old file with `history_base` (`thread_id` there is the old file's rollout ID, and `end_ordinal_exclusive` the first line not kept); the old file stays. kiroku shows the thread once: the newest such file (one no other file of the thread points at), read after the lines of the files it points at whose `ordinal` is below that bound. The turns reverted away, and older files the current one no longer points at, are not counted. A `history_base` that points at another thread (a paginated fork) is not followed, as before
- Files edited in session details come from `apply_patch` calls: the file names after `*** Add File:`, `*** Delete File:`, `*** Update File:` and `*** Move to:` in the patch (`apply-patch/src/parser.rs`). The patch is the `input` of a `custom_tool_call` or of a `function_call` named `apply_patch`, or is passed through the shell (including a `local_shell_call`) (`["apply_patch", patch]` or a heredoc such as `bash -lc "apply_patch <<'EOF' …"`). Only text with `*** Begin Patch` counts
- "Long conversations" takes the context window from `model_context_window` in `token_count` events (the largest value for the model of the response that read the most context)
- Titles come from `session_index.jsonl`
- `kiroku serve` watches only `sessions/`, `archived_sessions/` and `session_index.jsonl` (not logs or other state under `~/.codex`), and rereads only the threads whose files changed (a parent thread together with its subagents)
- Estimated cost uses OpenAI's standard prices (`OpenAIPrices` in `internal/core/usage.go`, from [the pricing page](https://developers.openai.com/api/docs/pricing); the numbers are kept in [upstream/openai-pricing.md](upstream/openai-pricing.md)). Input without the cached and cache-write tokens is priced as input, `cached_input_tokens` as cached input, `cache_write_input_tokens` as cache writes (as input for models with no cache-write price) and `output_tokens` as output (reasoning tokens are part of it). A response whose input (including cached tokens) is over 272K tokens is priced at the long-context rates as a whole; this needs per-response usage (`token_usage_record` or `last_token_usage`), so older rollouts that only have running totals use the standard rates. The history records the service tier that was requested (`thread_settings_applied.thread_settings.service_tier`, such as Fast or Flex; kiroku does not read it yet), but not the tier that actually served each response, nor Batch or a regional endpoint, so those rates are not applied. Models older than gpt-5 are not in the table (they appear in "Data sources" as tokens not in the price table) and can be added with `--prices`. A model not in the table under its own ID, such as `gpt-5-codex`, gets the price of the longest ID it starts with (`gpt-5`) and is listed in "Data sources" as "priced as" that ID

## Git

Commits by you (`user.email`) are read with the local `git log` from the git repository in the session's working directory (cwd), and pushes from the reflog of remote-tracking branches ("update by push"). Environments without git, and locations that are not repositories, are skipped, as are network (UNC) paths on Windows. Since these folders may hold repositories someone else made, git runs without the system config and with the repository's settings that run programs (fsmonitor, hooks, pager, textconv and external diff) turned off, and never asks for credentials. `internal/gitlog/gitlog.go`

## History retention

Adapters that implement `Retainer` return the settings that delete old history. Claude Code reads `cleanupPeriodDays` from the managed settings files (`managed-settings.json`, then `managed-settings.d/*.json` in name order, later files winning, in the [system directory](https://code.claude.com/docs/en/managed-settings) for the OS), which outrank the user `settings.json`, and otherwise from `settings.json` (30 days by default). Only a whole number of 1 or more counts, and each file is read only when it is a regular file of at most 8 MiB holding a JSON object. Server-managed settings, MDM profiles, the Windows registry and project settings are not read. Since v2.1.248 Claude Code keeps sessions started or last continued in Claude Desktop or Cowork at any age unless `desktopSessionCleanupPeriodDays` is set or managed settings set `cleanupPeriodDays`; kiroku does not tell those sessions apart, so it reports the one period. Kiro Crew reads `session.archive_retention_days` the way Crew does: `config.json` in the Crew folder with `config.local.json` merged over it (the overlay wins), written as `{"session": {"archive_retention_days": 30}}`. It is 30 days when the key is missing, when the value is not a whole number (a numeric string such as `"45"` counts, as in Crew) and when a file is missing or broken; `null` or a negative number turns Crew's cleanup off, so no retention is reported. `0` makes Crew delete every archived record at its next cleanup; since `days: 0` means "unknown" in `Retention`, this is reported with `now: true`, and the view and `kiroku doctor` say the records are deleted within an hour. Crew writes every key to `config.json`, so the value counts as set only when it differs from the default 30, and the setting is suggested in `config.local.json`, which wins over `config.json`. Crew deletes the files in `sessions/archive/` whose modification time is older than that, at most once an hour, and expires closed sessions' crew logs on the same setting. See [the guide's "History retention"](guide.md#history-retention) for details

Copies with `kiroku archive`: adapters that implement `Keeper` (Claude Code, and Crew's part of Kiro CLI) return the source locations to keep and where to put the copies. When on, `internal/archive.Sync` runs before reading and compresses each `.jsonl` in the source location to a `.jsonl.zst` at the same relative path (only files whose modification time changed; if the source location is a symbolic link, the target is kept). When reading, only copies whose original file is gone are added (Claude Code: `<archive location>/claude/<project>/<conversation ID>.jsonl.zst` and subagents; subagent files that were deleted are added from the copy even if the conversation itself remains. Crew: `<archive location>/crew/sessions/archive/`). When the original exists it is read instead, so nothing is counted twice

## Credits and model multipliers

Kiro credits are added up exactly as recorded in the history. Per-model multipliers are the ones Kiro applied when recording, and kiroku does not apply them again.

## What history records

Which facts each agent's local history records, and which only official docs give. It was checked against the agents' public sources ([openai/codex](https://github.com/openai/codex), [amazon-q-developer-cli](https://github.com/aws/amazon-q-developer-cli), [kirodotdev/kirocrew](https://github.com/kirodotdev/kirocrew)), official docs, and the reference implementations in [References](#references) (for Kiro IDE and Kiro CLI, whose formats are not documented). Update it when an adapter or an agent's format changes. Which metrics this leaves each agent with is in [the guide's "What each agent records"](guide.md#what-each-agent-records).

- **Read**: in the history, and kiroku reads it
- **Not read**: in the history, but kiroku does not read it yet
- **Docs only**: not in the history; only official docs give it, so kiroku carries it in code (for example the price table)
- **Not carried**: not in the history; official docs give it, but kiroku does not carry it in code or use it
- **None**: neither the history nor official docs give it
- **?**: not verified

## References
